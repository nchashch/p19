## Summary

After opening and closing the pause menu (Escape / Start) or the dev console while moving the
mouse, pressing W walks at an angle to where the camera points. The server's `CharacterLook`
yaw no longer matches the client camera's, and it never resynchronizes. Prediction on and off
are both affected.

## Steps to reproduce

Run in an isolated network namespace (avoids clashing with another local server), with a
`--no-render` client (it also reproduces with a rendered client):

```sh
unshare -rn sh -c 'ip link set lo up &&
  ./target/release/p19-server & ./target/debug/p19-client --no-render & sleep 8 && python3 repro.py'
```

`repro.py` (client BRP :15702, server BRP :15701):

1. `game/trigger {"event":"connect"}`, `game/select_level {"asset_path":"levels/minimal.level.ron"}`, `game/trigger {"event":"play"}`.
2. Five times: `game/mouse {"input":"motion","dx":80,"dy":0}`, then **in the same frame**
   `game/keyboard {"key":"Escape","pressed":true}` (release after 0.1 s), wait 0.5 s, Escape
   again to close.
3. Compare client `game/state.look_yaw` with server `server/state.players[0].look.yaw`; hold W
   for 1 s and compare the movement heading with both.

## Expected vs actual

- Expected: client and server yaw equal; W moves along the camera's facing.
- Actual: the server's yaw moves 0.4 rad per cycle while the camera stays at 0. After 5 cycles
  the client reads 0.0000 and the server −1.6000, and W moves along heading −1.6 (92° off the
  camera).

## Evidence

```
after pause cycle 1   client yaw +0.0000 server yaw -0.4000 Δ +0.4000
after pause cycle 2   client yaw +0.0000 server yaw -0.8000 Δ +0.8000
after pause cycle 5   client yaw +0.0000 server yaw -1.6000 Δ +1.6000
walk: moved (+12.67, +0.37) heading -1.6000; client yaw +0.0000 (off by -1.6000), server yaw -1.6000 (off by +0.0000)
```

Without menu toggles, random mouse bursts never diverged: Δ ≤ 0.0001 after 120 bursts, with
prediction off and on, over plain loopback and over `netem delay 40ms 15ms loss 2%`.

## Root cause

Confirmed. The client camera and the server look are two accumulators of the same replicated
`RotateCamera` `Fire` events: `controls.rs::rotate_camera` on the client, and
`p19_server::input::accumulate_look` on the server. They agree only if both see every event.

- `rotate_camera` was registered with the gameplay gate
  `console_closed.and_then(in_state(ModalMenuState::Closed))`.
- What reaches the server is gated by something else: `gate_replicated_input_context` setting
  `ContextActivity` in `Update`.
- Escape sets `ModalMenuState::Open`, and the transition applies in `StateTransition`, which
  runs before `FixedMain`. So in that frame's fixed tick, BEI fires `RotateCamera` with the
  frame's mouse delta, lightyear buffers it and sends it, and the server applies it. The
  client's observer, gated on the now-`Open` state, drops it.
- The context is only deactivated later, in `Update`. The console has the same window.

Every menu open with mouse motion in that frame adds a permanent offset.

## Fix

`rotate_camera` is registered ungated (`app.add_observer`). The context gate is the single
point that stops continuous look input, so the camera applies exactly the events the server
receives. A comment at the registration and AGENTS.md's "Console gating" convention record the
rule.

Verification, same repro after the fix, both prediction modes:

```
after pause cycle 5   client yaw -2.0000 server yaw -2.0000 Δ -0.0000
walk: moved (+11.71, +5.36) heading -2.0000; client yaw -2.0000 (off by +0.0000), server yaw -2.0000 (off by +0.0000)
```

The console path (Backquote) shows identical results.

## Follow-ups

- **Pitch is mirrored:** the client's `CharacterLook.pitch` (camera euler) has the opposite
  sign of the server's (`accumulate_look` adds `+y`). Measured client −0.3017 vs server +0.3017.
  It doesn't affect walking (ahoy derives ground movement from yaw), but anything that uses the
  server's pitch (swimming, future aiming) would see it inverted. Not fixed here.
- The temporary `ROTATE-FIRE` / `LOOK-DIVERGENCE` instrumentation from playtest 0012 (in
  `controls.rs`) was removed after this fix, together with a leftover `dbg!(&level)` in
  `p19_server::networking::load_level_request`.
