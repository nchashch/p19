## Summary

When the player looks down, the server's `CharacterLook.pitch` says they're looking up, by the
same amount. Walking is unaffected (ahoy's ground movement uses only yaw), but anything that
reads the server's pitch, such as swimming, aiming or hitscan, would see it inverted.

## Steps to reproduce

1. Connect, select `levels/minimal.level.ron`, play.
2. `game/mouse {"input":"motion","dx":0,"dy":100}` × 6, which looks straight down.
3. Compare `game/state.look_pitch` with `server/state.players[0].look.pitch`.

## Expected vs actual

- Expected: both about −1.57 (ahoy convention: positive pitch looks up).
- Actual: client −1.571, server +1.571.

## Evidence

```
looking down   client look yaw -0.000 pitch -1.571 | server yaw +0.000 pitch +1.571
looking level  client look yaw -0.000 pitch +1.429 | server yaw +0.035 pitch -1.429
```

## Root cause

Confirmed by reading the code at `4892d4d`:

- `rotate_camera` did `FpsCamera.pitch += value.y`, then
  `camera_transform.look_at(Vec3::Z.rotate_x(pitch).rotate_y(yaw))`. `look_at` points −Z at
  that vector, so the camera's euler pitch is the negation of `FpsCamera.pitch` (and its yaw is
  offset by π, hence the `yaw: −π` seed).
- `update_character_look` sent the camera's euler to the client's `CharacterLook`.
- `accumulate_look` added `+value.y` to the server's pitch, matching `FpsCamera.pitch`, not the
  camera.

So the two sides used opposite conventions.

## Fix

ADR 0017. `FpsCamera` now stores yaw and pitch in ahoy's convention, the camera's rotation is
derived from it (`Quat::from_euler(YXZ, yaw, pitch, 0)`), and that same pair is sent as the
`Look` input. Both sides apply it unchanged, so the server's look is the client's by
construction.

Verification:

```
looking down (mouse +dy)   camera yaw +0.000 pitch -1.561 | server yaw +0.000 pitch -1.561 | Δpitch +0.0000
after turn right           camera yaw -1.750 pitch +0.239 | server yaw -1.750 pitch +0.239 | Δpitch +0.0000
```
