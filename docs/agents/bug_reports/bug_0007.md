## Summary

With the in-game dev console open (backtick), typing WASD or Space still moves and jumps the
player character — the keystrokes meant for the console's input bar reach BEI's binding
readers on the replicated ahoy action entities and stream to the server as real input. The
console's own observers (hotkeys, UI actions) were gated behind `console_closed`, but the
*continuous* input path — the `Bindings` reading `ButtonInput<KeyCode>` every tick — was not,
and observers were never the thing feeding movement. The pause modal has the same leak
(movement/look continue while it is open), despite the intent recorded in `controls.rs`'s
build comment that gameplay pauses under it.

## Steps to reproduce

Windowed client, or the harness (the harness path used for verification; the windowed repro
is the same through real input events):

```sh
cargo build -p p19-server --release && cargo build -p p19-client --features dev-tools
./target/release/p19-server &
./target/debug/p19-client --features dev-tools &   # windowed, or --mcp for the harness
# harness:
curl -s http://127.0.0.1:15702 -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"game/trigger","params":{"event":"connect"}}'
# poll game/state → Lobby; server already InGame → play directly:
curl -s http://127.0.0.1:15702 -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"game/trigger","params":{"event":"play"}}'
# open the pause modal (Escape), then hold W:
curl -s http://127.0.0.1:15702 -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"game/keyboard","params":{"key":"Escape","pressed":true}}'
curl -s http://127.0.0.1:15702 -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"game/keyboard","params":{"key":"KeyW","pressed":true}}'
# poll game/state → position runs away from (0, 0.915, 0) while the modal is open
```

On a windowed client the console variant is the reported one: backtick → type WASD → the
character walks while typing.

## Expected vs actual

- **Expected:** with the console (or pause modal) owning the keyboard, gameplay input is
  frozen; the character stands still while typing.
- **Actual (pre-fix):** the character walks/jumps/turns under the open UI surface
  (BEI reads `ButtonInput<KeyCode>` every tick regardless of console state and streams the
  resulting action state to the server).

## Evidence

Verification run after the fix (playtest 0021, fresh `--mcp` client against the live
server, player spawned at (0, 0.915, 0)):

| Step | Observed |
|---|---|
| Baseline, no UI surface: `game/keyboard KeyW` held 2 s | position (0, 0.915, 0) → (−0.92, 0.915, −22.65) — moves |
| Pause modal open (Escape via BEI's real binding; `game/ui` shows the modal panel), `KeyW` held 2 s | position **unchanged** at (0, 0.915, 0) — frozen |
| Modal closed (Escape), `KeyW` held 2 s | position → (0, 0.915, −22.87) — moves again; gate releases cleanly |
| Panics/errors across the whole run | 0 |

## Root cause

The console gating convention (`add_observers_run_if!(…, console_closed)`) only gates
*observers* — one-shot event handlers. Movement is not observer-driven: `bind_replicated_ahoy_actions`
inserts `Bindings` on the server-authored replicated `Movement`/`Jump`/`RotateCamera` action
entities once, and BEI's binding readers then consume the raw device state every PreUpdate
tick, with lightyear streaming the resulting action state to the server. Nothing in that
continuous path ever looked at the console or modal state.

## Fix

`client/src/controls/controls.rs` — new polling `Update` system `gate_replicated_input_context`:
while the dev console is open **or** the pause modal is open, it deactivates the
`PlayerInputContext` context on the local player via BEI's own `ContextActivity<C>::INACTIVE`
(remove+insert; the component is immutable). Deactivation zeroes/releases every action state
of the context — the streamed state releases held keys server-side — while the bindings
survive untouched for reactivation on close. Escape/Tab live in the separate local
`PlayerControls` context, so the toggles keep working while gameplay input is frozen, and
the console's own toggle key reads raw `ButtonInput` upstream of BEI, unaffected.

The gating condition is the same expression the attack/kill observers already use
(`console_closed.and_then(in_state(ModalMenuState::Closed))` semantics), so both UI surfaces
and both input kinds (observers + continuous context) now share one gate.

### Verification limit, stated honestly

The console-open state itself could not be driven headlessly: chill_bevy_console's
`handle_toggle_key` reads `ButtonInput::just_pressed`, and `game/keyboard` writes land in
`RemoteLast` (end of frame) — the next frame's `keyboard_input_system` clears `just_pressed`
before `handle_toggle_key` (Update) ever runs. The live verification therefore exercised the
**modal** branch of the same gate system; the console branch differs only in reading
`ConsoleState.open` instead of `State<ModalMenuState>`, both feeding the identical
boolean. The user's windowed repro (console open, real key events) follows the same code path.
