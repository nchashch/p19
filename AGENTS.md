# AGENTS.md

This file provides guidance to AI coding agents when working with code in this repository.

## Agent skills (`docs/skills/`)

`docs/skills/` holds distilled, task-specific how-tos for agents working on this project — read the relevant one **before** attempting its task, it encodes hard-won gotchas that will otherwise cost you the same debugging time again:

- `docs/skills/playtest.md` — how to drive the game headlessly (launch the server + `--mcp` client, the `game/*` BRP methods, input injection semantics, screenshots, known failure modes, and how to write the typst playtest reports under `docs/playtests/`).

Existing playtest reports (`docs/playtests/playtest_*/report.typ`, screenshots in `docs/playtests/screenshots/playtest_*/`, compiled PDFs in the gitignored `docs/playtests/dist/`) are worked examples of what a completed agent playtest looks like — consult the latest one before writing a new one.

## What this is

A Bevy 0.19 (Rust, edition 2024) 3D game prototype. **Cargo workspace** with three members: `client` (the playable game — rendering, UI, input, camera, presentation), `server` (a real headless authoritative simulation server — physics, level loading, player spawning, movement/combat resolution), and `shared` (the simulation logic and network-message types both sides need to agree on: character controller, combat, player bundle, spawners, replication registration). No tests currently exist in the repo.

The workspace was built in anticipation of an "always multiplayer" architecture — even singleplayer would run a local client *and* server, simulation on the server / presentation on the client, so hosting real multiplayer later is "open a port" rather than a rewrite. That split is real: `server` is authoritative for level geometry (loads and instantiates `.glb` files headlessly via `bevy_gltf`/`bevy_world_serialization`/`bevy_skein`, generates real Avian colliders — see the "Server" section below), player spawning, and movement resolution (real, since the ahoy migration — see the movement bullet in the gaps list below) and combat resolution (currently broken by a caster-resolution regression — see that gap in the same list). `client` sends intent as network messages and renders whatever the server replicates back; it does not decide outcomes.

**Networking is `lightyear` 0.30** (UDP/netcode transport, workspace feature list `["avian3d", "udp", "netcode"]`) — this fully replaced `bevy_replicon`/`bevy_quinnet` (see `fc61710` in git history); there is no trace of either left anywhere in the codebase, and no QUIC. `shared::replication::SharedReplicationPlugin` is the single place both binaries register what crosses the network: `app.component::<T>().replicate()` per replicated component, `app.register_message::<T>().add_direction(NetworkDirection::...)` (+ `.add_map_entities()` for any message carrying an `Entity`) per message type — see the "Shared simulation" section for the full current lists. `bevy_asset_loader` is a real, load-bearing dependency — `client::assets::collections::CommonAssets` is the client's actual asset manifest, loaded through a `LoadingState` scoped to `GameState::AssetLoading` before the app ever reaches `MainMenu`, and `server::main` similarly gates `ServerState::Startup → Lobby` on `shared::assets::level::LevelMetadataAssets` finishing loading.

**Room-based interest management is real and wired up**, not scaffolding: `server::rooms::GameRoomPlugin` allocates two persistent rooms (`GameRoom`/`LobbyRoom`, via lightyear's `RoomAllocator`) at `Startup` and spawns two persistent root entities, `shared::level::InGameRoot`/`LobbyRoot`, each tagged with its own room (`Rooms::single(...)`). Anything `ChildOf`-parented under one of these roots inherits its room membership automatically (`HierarchySendPlugin::<ChildOf>`'s cascade — already active via lightyear's own server plugin group, no extra registration needed). A client's connection entity gets `Rooms::single(lobby_room)` the instant it connects (`server::lobby::join_lobby_room_on_connect`) and `Rooms::single(game_room)` once it actually joins the game (`server::networking::in_game_request`, which *replaces* its room membership, not adds to it) — so a client only ever receives replicated data for whichever room it's currently a member of.

**A real, significant architecture change worth internalizing**: the player character is **no longer the client's own connection entity**. For most of this project's history "the client's own connection entity doubles as its player character" was the design (and is still how `AttackAttempt`/`KillAttempt`/`SpawnCubeRequest`/`SpawnNpcRequest` resolve *who's acting* — always the sending connection's own entity, never a client-supplied field; note however that the *systems* consuming those messages still have stale pre-M2 assumptions — see the caster-resolution gap below). It's now different: the player character is a **separate entity**, spawned by `server::networking::in_game_request` as a `ChildOf`-child of `InGameRoot`, owned by the connection entity via a real, non-self-referential `ControlledBy { owner: connection_entity, .. }`. This was a deliberate fix (a self-referential `ControlledBy` — `owner` pointing at the entity it's *on* — gets silently stripped by Bevy's relationship-validation system, which was blocking replication of sibling components on that same entity) and is more idiomatic lightyear besides, but it means `shared::player::player()`'s bundle no longer lives on the connection entity — don't assume entity-identity between "the connection that sent this message" and "that connection's player character" anymore; resolve the latter via `ControlledBy`/`ControlledByRemote`, or client-side via `lightyear::prelude::Controlled` (see `client::gameplay::player_character`'s `LocalPlayer` mechanism).

**What's still genuinely missing or actively broken**, worth not assuming exists — several of these are new or newly-confirmed, not a stale carryover list:

- **Movement is server-authoritative and client-predicted, driven by ahoy's KCC on both binaries** (the ahoy migration, M0–M2, complete — see `docs/adr/0008` for the full decision/history): the server spawns the player's input context + action entities (bare, unbound — in `player()`'s bundle), the owning client binds real inputs to the replicated action entities (`controls.rs`'s `bind_replicated_ahoy_actions` — a **polling `Update` system**, not `On<Add, …>` observers, for the same replication-arrival unreliability that makes `on_player_spawned` poll; self-terminating via `Without<Bindings>`; gated on `Controlled` on the context entity; the `Bindings` insert is what auto-adds `InputMarker` and starts the `BEIStateSequence` stream), and both sides run ahoy's KCC over that stream (`AhoyPlugins` in both mains; headless-safe: `InputPlugin` disables BEI's raw-input systems on server-only builds). `PredictionTarget` (on the player spawn, scoped to the owning client via its connection entity's `RemoteId`) makes the client's local sim the prediction, reconciled by lightyear's rollback. The client's camera and the server's `CharacterLook` accumulator (`server::input`) are **the only consumers of the rotate actions** — see the BEI consumption rule below. Key wiring facts, all "confirmed by testing" during the migration:
  - **ahoy's KCC authors `Transform`** (its `run_kcc` final write) — both binaries' `LightyearAvianPlugin` must run `sync_to_transform: true` (NOT the default), or `Position` (and thus replication + the visual sync) never receives the character's motion. The import only touches `With<RigidBody>` entities on `Changed<Transform>`; interpolated remote entities carry no `RigidBody` client-side.
  - **`RigidBody` must be replicated** — without it, replicated colliders are *loose* client-side (no `ColliderOf` attachment), and ahoy's collision query (which requires `Position`/`Rotation`/`ColliderOf` on collider entities) can't see any level geometry — characters fall through everything.
  - **BEI gives a binding's input to the first action that reads it each tick** — other actions reading the same input get zero ("already consumed"). Never bind one physical input to two actions: the duplicate look bindings (legacy `FpsCameraRotation` + ahoy `RotateCamera`, both on mouse motion) split the mouse deltas nondeterministically (~70-90% to the camera, the rest to the server's look), and the server's wish direction diverged from the camera — "movement locked to one axis". One consumer per input, always.
  - **The client must lead the server's timeline by enough ticks that tick-N input arrives before the server simulates tick N** — `InputTimelineConfig::default()` is `no_input_delay()`, which made every input arrive late (even on loopback: send in PostUpdate, arrives next tick's PreUpdate) → `server_late_input_mismatch` corrections fighting the prediction. `SharedInputsPlugin` inserts a 2-tick minimum delay (`balanced()` preset: up to ~50ms of latency covered by auto-recomputed input delay, then ~100ms of prediction before more). **Confirmed live (two-client session): the chronic fix holds — the corrections can still fire ACUTELY when a second client joins.** The joiner's initial replication burst (server serializing the whole level + player state, plus the existing client absorbing/rendering the new entity) hitches one side of the pipeline for ~10 ticks, blowing the 2-tick headroom: the established client's input packets then arrive 1 tick after the server simulated those ticks, producing a bounded run of `server_late_input_mismatch` ERRORs that self-heals once the burst passes. Benign (mostly sub-frame stick-drift corrections; worst case a ~170ms micro rubber-band), so we document instead of fixing — `balanced()`'s auto-recompute covers chronic latency, not acute bursts, and raising the delay floor would tax every input to guard against a rare event.
  - Ahoy's input observers write the **context entity's** `AccumulatedInput`, and its KCC runs on the entity carrying `CharacterController` — the two must be the same entity (the legacy `PlayerControls` context lives on a child entity and can't serve ahoy; the replicated `PlayerInputContext` context lives on the player itself).
  - BEI API gotchas: `Bindings::spawn` takes exactly ONE `SpawnableList` (modifiers are sibling components on the action entity, and presets like `Axial` can't nest inside per-binding `Spawn(...)` bundles); `Spawn` (bevy's) wraps a bare `Binding`; `ActionOf::get` needs `bevy::ecs::relationship::Relationship` in scope; `SpawnWith` is bevy's, not BEI's; `TypePath` is not auto-generated by `derive(Component)`.
  - VR locomotion mocks the same replicated actions (`ActionMock` per frame — the left stick as local movement, the head's global-rotation deltas as look; snap-turns ride the head deltas via the rig rotation). The mock overrides bindings for that update, so the "VR headset + keyboard together" combo currently degrades to mock-only movement — a known follow-up.
  - Remaining gaps in this area: ahoy's own KCC state components (`CharacterControllerState`/`AccumulatedInput`) are **not rollback-registered** — only `Position`/`Rotation`/`LinearVelocity`/`AngularVelocity` are (lightyear_avian's registrations) — so KCC-internal state (coyote/jump-buffer stopwatches, grounded hit data) isn't rewound on corrections; other players aren't interpolated yet (no `InterpolationTarget` — they follow via replicated `Position` + lightyear_avian's transform sync); NPC/AI input has no path yet (would be: server-side BEI mocking of an NPC context — ahoy's stated design goal, though see the debug-replay gap-list entry below: `ActionMock` doesn't actually work server-side in this project as currently wired, confirmed live via three separate diagnostic passes — that plan needs revisiting in light of this). The `kcc_debug` console command dumps the whole input→movement chain for diagnosing this class of breakage.
- **Fixed: no protection against loading a level twice, or a client re-requesting one.** `server::level_state::LevelState` (previously documented here as dead code) is now wired up: `load_level_request` rejects any `LoadLevelRequest` while a level is already `Loading`/`LevelLoaded`, logging why instead of silently spawning a second `WorldAssetRoot`/`PlayerCharacterSpawner` on top of the first — see the "Server" section's `level_state.rs`/`networking.rs` bullets for the mechanism. Confirmed live: 9 rapid duplicate requests against the old code left 9 stacked `PlayerCharacterSpawner`s (and correspondingly duplicated colliders/geometry) in the world — a plausible root cause for reports of the character controller/camera destabilizing after repeated reconnect-and-reselect-level cycles; the identical abuse pattern against the fix now rejects 8 of 9 and leaves exactly one spawner.
- **Caster-resolution regression: every client→server "act" message is silently dropped.** `server::spawn`'s `spawn_cube`/`spawn_npc` and `server::combat`'s `resolve_attack`/`resolve_kill` still assume the pre-M2 architecture — they look the caster's `Gcd` (and, in combat, the caster's `Transform` for the `ATTACK_RANGE` check) up **on the connection entity** (`casters.get_mut(receiver_entity)` / `positions.get(killer)`). Since the player became a separate entity, the connection entity has neither `Gcd` nor `Transform` — those live on the player character — so every request dies at its `continue` guard with no log line. Confirmed live: cube/NPC spawn hotkeys and agent `game/trigger spawn_cube` produce no `Cube`/`Npc` entities at all. The fix shape: resolve the sender's player character from its `ControlledBy { owner: connection }` (or insert a `Gcd` on the connection at player-spawn time) before the cooldown/range checks.
- Cleanup of a disconnecting client's non-connection-entity `Replicated` entities is still a gap — and now more consequential, since the player character is a separate entity (see above) spawned with `ControlledBy { lifetime: Lifetime::Persistent, .. }`. `Persistent` is lightyear's own "don't despawn this when the owner disconnects" option, so a disconnected player's character currently lingers in the world indefinitely. **Live-confirmed knock-on (the "can't connect a second time" bug's visible half)**: a *new* client connecting receives the zombie's replicated `ClientInGame` the instant its initial sync lands, which fires `on_in_game` and drops the client into `GameState::InGame` — but the zombie's `ControlledBy.owner` points at its *dead* connection entity, so the new client never gets `Controlled`/`LocalPlayer`: no local player, no `position` in `game/state`, no way to progress. Restarting the server is the only current workaround.
- **Fixed**: `client/src/controls/controls.rs`'s `return_to_main_menu` used to be a live `todo!()` — triggering that path (bound to Escape/gamepad Start, also `modal_menu.rs`'s pause-menu "Main Menu" button and its VR wrist-panel equivalent) panicked the client. Now mirrors `ui/lobby.rs`'s already-working `lobby_main_menu_button`: `commands.trigger(Disconnect); commands.set_state(GameState::MainMenu);` — `Disconnect` is this crate's local event (`crate::events::Disconnect`), routing through `lifecycle::networking::on_disconnect_request`'s established two-part disconnect (`lightyear::prelude::Disconnect` + `Unlink` — see that function's own doc comment for why triggering lightyear's `Disconnect` alone leaves a stale `Linked` marker that panics on the next connect attempt). Verified twice: first via `docs/playtests/playtest_0005/` against the equivalent code path (`game/trigger disconnect` while in-game — at the time, the tool API had no way to simulate the actual keypress/button-click); then, once `game/gamepad` existed (see the tool-API bullet above), via the *literal* crash path itself — real simulated gamepad Start (open the pause modal) → DPadUp (navigate focus from the auto-focused "Resume" to "Main Menu") → South (activate it) — confirmed no crash and a clean `GameState::MainMenu` transition, see `docs/playtests/playtest_0006/`.
- **Fixed: a real mouse click on the lobby's "Play" or "Main Menu" button never worked, at all, ever — not "under certain conditions"**, found via a full keyboard+mouse+gamepad reachability sweep once `game/mouse` existed to make the literal click testable. Root cause: `client/src/ui/lobby.rs` imported `Activate` from `crate::ui::widgets` (the pre-`bevy_feathers` hand-rolled type, still correct for `widgets::button()` — the HUD and pause modal) instead of `bevy::ui_widgets::Activate` (the real event a `FeathersButton`/`menu_button()` press emits — see `selector.rs`'s or `ui.rs`'s correct import). Since `lobby_play_button`/`lobby_main_menu_button` are both `menu_button()`-based (`FeathersButton`, same as every other menu/lobby button in the app), a genuine mouse click on either only ever produced the *real* `bevy::ui_widgets::Activate`, which these two handlers — listening for the wrong type — never received. It only *looked* input-method-dependent because `ui.rs`'s `on_ui_confirm` (gamepad South) and `on_ui_confirm_enter` (literal Enter) both *also* fire the legacy `LegacyActivate` as a compatibility bridge for old-style widgets — which happened to be exactly the (wrong) type these two handlers were listening for, accidentally masking the bug for every input path except a real click. This is very likely the exact mechanism behind a bug the project owner had independently noticed and described before this investigation: "click Play with the mouse... under certain conditions, you won't get in game, but navigate to it with arrow keys+Enter or a gamepad and it works" — this fix makes it work unconditionally for all three input methods, not conditionally for two of them. Diagnostic trail worth knowing if anything like this resurfaces: real clicks correctly generated `Pointer<Press>`/`Pointer<Release>` and the `Pressed` marker correctly appeared and disappeared the whole time (ruling out a picking/hit-testing bug or a `ServerState::Loading` race — the server was already `InGame` in most repro attempts), but `Activate` itself silently never fired; `world.trigger_event`-injecting the correct `bevy_ui_widgets::Activate` directly onto the button entity did NOT fire the handler either (further confirming a listener-type mismatch, not an event-delivery problem), while `game/gamepad`'s South button worked throughout every attempt. After the fix, verified via `game/mouse`: a mouse click on "Play" immediately after selecting a level (the exact reported race-looking scenario) now reaches `GameState::InGame`, and "Main Menu" now correctly disconnects — both confirmed with a fresh server+client pair, not reused state. **Independently confirmed by the project owner on the real windowed client** (not `--mcp`): Connect → select a level → click Play, all with the mouse, works end-to-end; literal Enter also works there — exactly what the `dispatch_focused_input`/`PrimaryWindow` gap noted below predicts, since a real window always has one.
- **Fixed on the same pass, but silent/never independently reported**: `docs/skills/playtest.md`/`AGENTS.md`'s **"only rely on inputs a human could enter" reachability sweep also surfaced a `--mcp`-headless-only structural gap, not a gameplay bug**: `bevy_input_focus::dispatch_focused_input` (the system that turns a raw `KeyboardInput`/`MouseWheel` event into the `FocusedInput<T>` a focused widget's native key handler reacts to) hard-requires a `Query<Entity, With<PrimaryWindow>>::single()` to succeed, and returns early (silently skipping its whole body, no error) otherwise — confirmed via `world.query` for `bevy_window::window::PrimaryWindow` returning `[]` in `--mcp` mode (`WindowPlugin { primary_window: None }`). Practical effect: **literal keyboard Enter can never activate a `FeathersButton` (main menu, lobby, any selector row/popup) through the `--mcp` harness**, no matter how `game/keyboard` injects the key — `bevy_ui_widgets::button::button_on_key_event` never gets a `FocusedInput<KeyboardInput>` to react to, headlessly. This is not fixable from the tool-API side (the gap is in Bevy's own focus-dispatch system, gated on a resource `--mcp` mode deliberately never creates) and is not believed to affect a real windowed client (which always has a `PrimaryWindow`) — every other input path (mouse click via `bevy_picking`, gamepad South via `on_ui_confirm`'s direct trigger, and literal Enter on the *old* hand-rolled `widgets::button()` via `on_ui_confirm_enter`'s `LegacyActivate` bridge, which needs no window at all) works fine headlessly and was cross-verified against this specific limitation during the same sweep — e.g. the pause modal's Resume/Main Menu buttons (`widgets::button()`-based) correctly respond to literal Enter headlessly, while the main menu/lobby's `FeathersButton`s correctly do not, matching this mechanism exactly.
- `client/src/lifecycle/loading.rs`'s `clear_effects` is fully written, with a substantial doc comment about VR `XrTrackingRoot` reparenting, but is never called from anywhere — dead code, not active cleanup, despite reading like it should be.

- **`--mcp` (CLI flag or config.toml `mcp = true`) runs the client as a headless agent host** (see `config::is_mcp_mode_presync` + the headless branch in `client/src/main.rs`): **no winit at all** (disabled + `WindowPlugin { primary_window: None, exit_condition: DontExit }`), `ScheduleRunnerPlugin::run_loop(1/60)` drives frames (the `--headless-render` variant drops this to 2 fps — logic stays 60 Hz via catch-up — and spawns an `ObserverCamera` instead of expecting a player; it joins worlds via `game/trigger observe`, and its `game/screenshot` accepts a `camera` entity whose `RenderTarget` is temporarily borrowed onto a dedicated capture texture and restored after the capture). `controls/camera.rs`'s `OffscreenRenderTarget` (1280×800 — the Steam Deck's native 800p) + `retarget_cameras_to_offscreen` point *every* camera (loaded-world cameras, the player camera, the startup `Camera2d` for the menu UI) into that texture — so UI/rendering all still run, and `game/screenshot` captures the texture (`Screenshot(RenderTarget::Image)`). The retarget also **re-orders and de-clears claimed cameras**: all claimed cameras share ONE texture, and a camera left on `ClearColorConfig::Default` erases every camera that rendered before it (the loaded glTF worlds spawn cameras whose target is `RenderTarget::None { .. }` — also claimed), so the first-claimed camera keeps the clear (base layer, order 1) and each later claim gets the next order + `ClearColorConfig::None` — the most recently arrived camera's 3D view wins (the player camera arrives after the level's authored one, so the agent sees through the player's eyes in game). `game/screenshot` writes **persistent, timestamped PNGs to `docs/playtests/dist/screenshots/`** (optional `{"label": "..."}` param names the file; `game/screenshot/get` reports the newest capture's base64 WITHOUT consuming it) so a human can browse exactly what the agent saw. No display is needed, so the same binary runs on GPU-less VPSes with a software Vulkan driver (lavapipe). Caveats: `--mcp` and `vr = true` are incompatible (`--mcp` wins); the 2× `UI_SCALE` overflows the 800p offscreen target (the menu renders partly cut off — cosmetic, bump the resolution if it matters); the real mouse/keyboard do nothing (no window — agent input only), but agent-injected input via `game/keyboard`/`game/mouse`/`game/gamepad`/`game/input` all work, including real UI clicks through `game/mouse` (confirmed live: clicking "Connect"/"Options" at their actual screenshot pixel coordinates drives the real `bevy_ui`/`bevy_picking` pipeline, not just mouse-bound gameplay actions). ## Platform targets

Steam Deck is the primary/min-spec target, not a secondary port — most of the realistic install base (Deck itself, other handhelds, gaming laptops, older desktops) is roughly Deck-class hardware, and tuning for a fixed console-like spec first is an easier bar to hit reliably than an unbounded PC hardware matrix. A higher-end PC gets a fidelity bump (heavier AA, higher shadow/texture resolution, larger draw distance), not different content — what actually exists in the world at a given position must stay identical across hardware, since this is a multiplayer game and letting quality settings change *what's loaded*, not just how it's rendered, would desync what different players in the same session can see/interact with.

The concrete number this is designed against is Deck's ~4GB VRAM budget — already a real constraint the asset pipeline is built around, not a future concern:
- The KTX2-compressed-texture and BC6H-compressed-skybox pipelines (`scripts/hdri_to_skybox.py`, `glbpack.sh`) already cut real assets 3-4x smaller on disk and in VRAM, confirmed by direct measurement (e.g. one skybox: 192→24 MiB VRAM).
- The scaling model this points toward: a texture-quality setting resolves the *same* `#[asset(key = "...")]` keys `CommonAssets`/`PreloadCollection` already use against different source directories or mip-stripped KTX2 variants (1K/2K on Deck, 2K/4K on a high-end PC) — the streaming/proximity-loading logic stays quality-tier-agnostic, only the manifest paths and the VRAM-budget number it's checked against change.
- `PreloadCollection` (see the `assets/` bullet below) exists specifically to keep total resident VRAM under budget on Deck by only keeping nearby content loaded — not purely a pop-in/loading-screen concern, a genuine memory-pressure mechanism a beefier PC target wouldn't strictly need but benefits from anyway. **Correction to an earlier version of this doc**: there is no `PreloadBeacon` component anywhere in the codebase — it's mentioned exactly once, as prose in a `TODO` block comment in `shared/src/assets/level.rs`, describing a hypothetical future dev-tool validator. Don't go looking for it as real, wired-up code; `PreloadCollection` itself is real but currently unused (not loaded via any `LoadingState`, not referenced anywhere outside its own definition).

Also relevant to "Deck Verified" specifically: `input_icons.rs`/`hud.rs`'s `controls_tips` already render real Steam Deck button glyphs (`steam_deck_atlas_image`/`_manifest` in `CommonAssets`), and the existing gamepad-first UI navigation (`ui.rs`'s `menu_controls`, `MenuControls` input context) covers Valve's "default controls work" verification criterion without extra work — worth keeping in mind before assuming any Deck-specific UI/input work is still outstanding.

## Character authoring pipeline (design direction — mostly not implemented yet)

The goal is one data-driven, unified spawning system used identically for the player, NPCs, and eventually AI-driven enemies — several independently-authorable, independently-reusable axes per character, rather than a bespoke hand-built bundle per character type (`shared::player::player()`'s current hardcoded `PLAYER_*` constants are exactly what this is meant to eventually replace, though nothing has been migrated off it yet). The axes, deliberately kept orthogonal so any one can be swapped or reused without touching the others:

- **Rig** (`assets/rigs/*.glb`, presumably split under `character`/`environment`/`prop` per the existing directory convention) — bones, animations, and Skein-authored gameplay markers: a bare `RigRoot` marker component (`assets::character::RigRoot`, no fields) on the armature's root empty, plus (not yet built) weapon/gear attachment-point empties, hit-registration collider empties, and a camera pivot. Deliberately excludes the visible mesh/materials — those live in a separate **skin** `.glb`, meant to be spawned as a swappable child so re-skinning a character doesn't touch its rig/gameplay setup. Not yet implemented, and genuinely nontrivial when it is: glTF skinning binds a mesh's joints to `Entity` indices within its *own* export, so an independently-exported skin `.glb` brings its own redundant copy of the bone hierarchy by default. Sharing the armature's live animated pose needs the skin's `SkinnedMesh.joints` re-targeted at spawn time to the armature's already-instantiated bones (matched by name), not just parented as a child — the same "find a named entity inside an already-instantiated rig" primitive that weapon/gear attachment points and the camera pivot will also need, worth building once as shared infrastructure rather than three times.
- **Controller** (`assets::controller::Controller`, `.controller.ron`, loaded via `RonAssetPlugin` registered in `main.rs`) — pure movement-feel data: `collider`/`ground_detection_collider` (`ColliderConstructor`), `acceleration`/`damping`/`jump_impulse`/`gravity`/`terminal_velocity`, `ground_detection_max_angle`/`max_distance`, `game_layer`. `assets/controllers/player.controller.ron` mirrors `shared::player::player()`'s current hardcoded values exactly, but nothing loads or applies it yet. Conclusion reached while designing this: nearly every character — player, NPCs, animals, robots — reduces to the same `MoveAndSlide` shape (one capsule/cylinder collider regardless of visual complexity; legs/wings/whatever are an animation-layer concern, not a collision one). The only real algorithmic outlier found is wheeled vehicles (raycast/suspension simulation, not a capsule sweep); earlier "mount"/"quadruped controller type" ideas turned out to just need different `Controller` *data*, not a different algorithm — so a `Controller` variant enum, if it ever grows one, likely only ever needs `MoveAndSlide` and `Vehicle`.
- **Stats** (`assets::stats::Stats`, `.stats.ron`, not yet registered as loadable) — RPG numbers (`vitality`/`strength`/`agility`/`intellect`/`luck`, plus whatever else accumulates). Deliberately meant to apply identically to the player and every NPC, not a player-only system — the design reasoning: if the player and every enemy are governed by the same stat/damage math, skill and system-knowledge the player builds against enemies genuinely transfers to reasoning about their own character, the way Dark Souls-style games are often praised for feeling fair even when difficult. `shared::combat.rs`'s current `DAMAGE`/`ATTACK_RANGE` are flat global constants applied to every attack regardless of attacker — `Stats` is meant to replace that with real per-character values, which needs `server::combat::resolve_attack`/`resolve_kill` to actually read a `Stats` component rather than a shared constant, a real behavior change, not just moving numbers into a file.
- **Abilities** — not yet stubbed in code at all. The intent is a shared "ability grammar" (cooldown, range, damage/effect shape, animation/VFX hooks) that both the player's hotbar (`hud.rs`) and an NPC's AI-selected action draw from the same asset pool, rather than bespoke Rust per ability. `shared::combat::Gcd` (the existing shared global-cooldown component) is a working precedent this would extend, not a new pattern.
- **`Character`** (`assets::character::Character`, `.character.ron`, e.g. `assets/characters/player.character.ron`) — the aggregation point: `rig`/`controller`/`stats` fields, each a bare `AssetServer` path, *not* an id looked up through a manifest file. A `manifest.toml`-style id→path indirection was tried first (`client/assets/controllers/manifest.toml`, now stale/unused) and deliberately dropped: it's a second file that can silently drift from the paths it's supposed to index — the same category of bug the `PreloadBeacon`/`preload_collections` divergence problem (see the asset-streaming design further up) was built to eliminate, and precisely the reason it's still only a design, not real code (see the correction above — it's not real yet). Pasting a literal asset path into Skein's data panel has no such failure mode. Whatever eventually resolves a `Character` into a real spawned entity (not implemented yet) is expected to spawn `rig`, wait for `WorldInstanceReady`, find the `RigRoot`-tagged descendant, and insert the components resolved from `Controller`/`Stats` directly.

Two existing systems are worth knowing aren't symmetric between player and AI yet, since making them so is exactly what this design is for:
- **Movement *is* symmetric now** (the ahoy migration): the player's input is replicated BEI action state, and ahoy's own docs call input mocking the intended path for NPC/AI input — a server-side AI system would mock an NPC context's actions exactly like the client's replicated stream mocks the player's (see `server::input`'s player-side analogue). `polyanya`/`rerecast` (vendored navmesh pathfinding/generation, see Dependency layout) are the not-yet-wired pieces an AI steering system would connect through this path.
- Combat is *not* symmetric yet: `AttackAttempt`/`KillAttempt` are `shared::client_events` types, and `resolve_attack`/`resolve_kill` are systems scoped specifically to incoming `MessageReceiver<AttackAttempt>`/`MessageReceiver<KillAttempt>` — today only a real connected network client can trigger an attack, there's no path in for AI at all. Closing that needs the same shape of fix as movement got: extract the actual resolution logic so it's reachable both from a real client's message and directly, with no network hop, from a server-side AI decision.

Worth knowing this design converges with, not diverges from, how commercial engines actually do this at scale — not a coincidence, the same production pressures (many characters, many designers, live tuning without recompiling) push toward the same shape: Unreal's `CharacterMovementComponent` drives player- and AI-controlled pawns through the identical component for the identical reason as the `Controller`/AI-reuse design above; Unreal's Gameplay Ability System (`AttributeSet`/`GameplayAbility`/`GameplayEffect`) is a shipped, commercial answer to exactly the "one system, used identically for player and NPCs" goal behind `Stats`/abilities here. Unity's `CharacterController` component plus `ScriptableObject` data assets are the same shape at the movement/data-externalization layer. The one real gap versus those engines: no visual/GUI editor for any of this — `Controller`/`Character`/`Stats` are hand-authored RON text files, which is a real production-ergonomics tradeoff for a larger team, offset by being trivially diffable/merge-friendly in a way binary serialized asset formats usually aren't.

**Current implementation status**, to avoid a future session assuming more of this is built than actually is: only the `Controller`/`Character`/`Stats` struct definitions and their example `.ron` files exist. `RonAssetPlugin::<Controller>` is registered in `main.rs`; `Character`/`Stats` are not yet registered as loadable assets. Nothing resolves a `Character`/`RigRoot` into spawned components — `shared::player::player()` is still completely independent of all of this. Abilities have no code at all yet, not even a struct. The armature/skin split, attachment points, hit colliders, and camera pivot are pure design, nothing authored or spawned.

## Commands

```sh
cargo build -p client --release   # build of the game
cargo build -p server --release   # build of the server
cargo build --workspace --release # build everything
cargo run -p client --release     # run the game (connects once the main menu's Connect button is pressed, not on startup — see config.toml below for the address)
cargo run -p server --release     # run the authoritative headless server (listens on 0.0.0.0:6000, UDP/netcode)
cargo check --workspace           # fastest way to verify compile errors across all members
cargo clippy --workspace
```

There is no test suite. Run commands from the workspace root (`prototype_19/`) — Bevy's default asset resolution is relative to each crate's own `CARGO_MANIFEST_DIR` at compile time, not the process's CWD, which is why `assets/` lives inside `client/` (`client/assets/`) rather than at the workspace root; moving it back out will break client-side asset loading. `server/assets/` is a **separate**, real directory (see the "Server" section — it used to point at `client/assets/`, that's no longer true) holding server-side level manifests/geometry (`server/assets/levels/`, `server/assets/rigs/`). `assets_src/` (raw `.blend` files and downloaded source-asset packs, exported/processed into `client/assets/` for actual runtime use — nothing loads from it directly) lives at the workspace root instead, alongside `client/`/`server`/`shared`, not inside `client/`.

`../build.sh` (one level up, outside this workspace) cross-builds a release binary inside a `steamrt-sniper` podman container for Steam Runtime compatibility. It runs `cd prototype_19 && cargo build --release`, which now builds the whole workspace — any packaging step downstream that expects a binary literally named `prototype_19` needs updating to `client`/`server`.

For testing inside the `steamrt4` toolbox (a lighter-weight alternative to `../build.sh`'s podman container — see `steam_deck_toolbox.sh`) or copying a binary to an actual Steam Deck: **always build with `./steam_deck_toolbox.sh cargo build -p <client|server> --release`** (or `toolbox run -c steamrt4 -- cargo build ...` directly — the script is just a thin wrapper around that; run bare with no args, it enters the toolbox interactively instead), never a plain host-side `cargo build`/`cargo run` for a binary that's going to run inside the toolbox or on the Deck. The toolbox and host share the same `rustc`/`cargo` toolchain via the bind-mounted home directory, so cargo's own fingerprinting genuinely cannot tell the two environments apart and won't force a relink on its own — a host build silently produces a binary linked against the host's (newer) glibc, which then fails on the toolbox's or Deck's older glibc with `GLIBC_2.4x not found` errors, even though nothing about the *build* looks wrong from the host's side. Recovering from this needs `cargo clean -p <crate> --release` before rebuilding inside the toolbox — deleting just the final binary isn't enough, since cargo can still decide only a relink (not a full recompile) is needed and reuse the host-tainted intermediate objects. Verify with `objdump -T target/release/<bin> | grep -oE 'GLIBC_[0-9.]+' | sort -Vu | tail -5` — a toolbox-built binary should top out around `GLIBC_2.39`, well under the toolbox's/Deck's actual baseline (`2.41` as of this container image), not `2.43`/`2.44`.

`scripts/deploy_steam_deck.sh` builds `client --release` inside the toolbox (`cargo clean -p client --release` first, guarding against the exact glibc-taint bug in the paragraph above), stages the binary + `client/assets/` into `steam_deck_staging/`, and sanity-checks the linked GLIBC baseline — ready to hand straight to SteamOS Devkit Client's Title Upload (`Local Folder` = `steam_deck_staging/`, `Start Command` = `./client`).

Tracy profiling (`cargo run -p client --release --features tracy`) is **opt-in**, not part of any default feature set — see `client/Cargo.toml`'s comment on the `tracy` feature. `bevy/trace_tracy` makes `tracy-client` buffer every instrumented span in memory until an actual Tracy GUI connects and drains it; with the feature always-on, a normal play session with no Tracy attached was a real incident (`cargo run -p client --release` ran RSS from ~9GiB to 40+GiB in under 4 minutes at ~150MB/s). Only build with `--features tracy` when you intend to actually attach Tracy and keep it attached for the run. The workspace root's `[profile.release] debug = true` (in `Cargo.toml`) exists so Tracy shows real function names instead of addresses — it applies to `server` too (harmless there, just a bigger binary) since Cargo profiles aren't per-member.

`client/assets/config.toml` (`server_ip`, `vr` — see `client/src/config.rs`'s `ClientConfig`) is the only way to point the client at a non-default server address or VR mode; there's no in-game UI for either (the main menu used to have a player-name/IP text field, removed in favor of this file). Both fields fall back gracefully if the file is missing or absent — `vr` defaults to `false` (`#[serde(default)]`), `server_ip` falls back to `"127.0.0.1"` — so a missing or partial `config.toml` degrades rather than fails to start. There's no `level` field any more — which level to load is a runtime choice made from the lobby UI (see below), not a config file default.

## Dependency layout

Root `Cargo.toml` is the workspace manifest: `[workspace.package]` for shared `edition`/`version`, `[workspace.dependencies]` centralizing every dependency's version (or local path) in one place. Member `Cargo.toml`s reference them via `dep.workspace = true` rather than redeclaring versions. Two things worth knowing if you touch this:
- A member **cannot** override `default-features` on a `dep.workspace = true` reference, even if the workspace entry explicitly sets `default-features = true`. `server`/`shared` need a smaller `bevy` feature set than `client` (headless, no rendering), so they declare `bevy` directly with their own `default-features = false` instead of inheriting it — see `server/Cargo.toml`/`shared/Cargo.toml`.
- Path dependencies in `[workspace.dependencies]` resolve relative to the **workspace root** (where the root `Cargo.toml` lives), not relative to whichever member references them. The workspace root is at the same location the old single-crate root used to be, so these paths are unchanged from before the workspace split (`../bevy_mod_outline`, etc. — not `../../`).

`lightyear` (`version = "0.30.0", features = ["avian3d", "udp", "netcode", "input_bei", "debug"]`) and `lightyear_avian3d` are real, load-bearing dependencies of all three workspace members (`client`, `server`, and `shared` itself — `shared/src/replication.rs` imports `lightyear::prelude::*` directly) — this is the entire networking/replication stack: `server::ServerPlugins`/`client::ClientPlugins`, `MessageSender`/`MessageReceiver<T>`, `Replicate`, room-based interest management (`Rooms`, `RoomPlugin`, `RoomAllocator`), and the UDP/netcode transport itself. No `webtransport` feature — this project doesn't use QUIC. `lightyear_inputs_bei` (0.30, per-binary feature: `client` in `client/Cargo.toml`, `server` in `server/Cargo.toml`; `shared` declares it bare) networks BEI action state for the prediction pipeline — registered via `shared::inputs::SharedInputsPlugin` around the `PlayerInputContext` context type (the M0-era `TestControls`/`TestAction` placeholder pair was renamed/deleted in M2). **The non-obvious part (confirmed by testing — without it the client panics at connect with "Resource does not exist: LastConfirmedInput")**: the `lightyear` meta-crate entry also needs the `input_bei` feature — `LastConfirmedInput` is initialized by a `LastConfirmedInputPlugin` inside `lightyear_inputs` that only compiles when `lightyear_inputs/prediction` is on, and the meta-crate's `prediction` feature reaches that only via its `lightyear_inputs?/prediction` passthrough, which only activates when `lightyear_inputs` is the *meta-crate's own* dependency (i.e. `input_bei` is enabled). Depending on `lightyear_inputs_bei` directly (as this repo does, for the import path + per-binary features) does nothing for that chain. Related: `InputPlugin` adds `EnhancedInputPlugin` itself, so `controls.rs`'s own add of that plugin is guarded with `is_plugin_added` — it used to be the only adder and panics if double-registered. `bevy`'s `system_font_discovery` feature (workspace `Cargo.toml`) is unrelated to networking — it lets `parley` (Bevy 0.19's text-shaping stack) fall back to a host-installed CJK font for glyphs `CommonAssets.serif_font` doesn't cover (the `ja-JP` locale exercises this); client-only in effect, since `server`/`shared` declare their own smaller `bevy` feature sets and never render text. `debug` (added this session) pulls in `lightyear_tools` for structured `lightyear_debug::*` tracing — see the gap-list's "Added: `lightyear`'s `debug` feature" bullet for the full mechanism.

Several dependencies are **not** pulled from crates.io — they're path-dependencies on sibling checkouts one directory up from the workspace root (`../<crate>`), i.e. forked/vendored versions of these libraries:

- `polyanya` (`../polyanya`) — navmesh pathfinding
- `rerecast` (`../rerecast/crates/rerecast`) — navmesh generation
- `bevy_mod_outline` (`../bevy_mod_outline`) — selection/hover outlines
- `bevy_vello` (`../bevy_vello`) — vector graphics rendering
- `bevy_seedling` (`../bevy_seedling`) — audio
- `audionimbus` (`../audionimbus/audionimbus`) — spatial audio
- `bevy_tui_texture` (`../bevy_tui_texture`) — ratatui-as-GPU-texture UI panels

If something doesn't behave like upstream docs suggest, or a symbol can't be found, check the sibling checkout's source directly rather than assuming crates.io behavior — these may be patched/ahead-of/behind the published versions. `bevy_mod_outline` in particular carries a local fix: `pipeline_key.rs`'s `DerivedPipelineKey::new` used to force `motion_vector_prepass` to `false` for the `Stencil`/`FloodInit` pass types regardless of the view's actual state, which crashed (wgpu bind-group-layout validation error) when outlining a skinned mesh with `TemporalAntiAliasing` enabled. Fixed by letting them inherit the view's real flag like the `Volume` pass type already did. Worth upstreaming; if this crate is ever re-vendored, check whether the fix needs reapplying.

`bevy_oxr` (`../bevy_oxr`, providing `bevy_mod_openxr`/`bevy_mod_xr`/`bevy_xr_utils` — see the VR/OpenXR paragraph below) carries a similar local fix: `bevy_xr_utils::tracking_utils::TrackingUtilitiesPlugin`'s controller-grip tracking creates and attaches `left_pose`/`right_pose` OpenXR actions but upstream never actually suggests bindings for them (`app.add_systems(OxrSendActionBindings, suggest_action_bindings)` was commented out in `crates/bevy_xr_utils/src/tracking_utils.rs`), so the action spaces never locate to a real controller pose — both `XrTrackedLeftGrip`/`XrTrackedRightGrip` entities stay at the same untracked identity transform, which looked like "one box, no tracking" when first tried. Fixed by uncommenting that line (and importing `OxrSendActionBindings` from `bevy_mod_openxr::action_binding`). Also worth upstreaming; check whether it needs reapplying if this crate is re-vendored.

`bevy_tui_texture` (`../bevy_tui_texture`, checked out at the matching `v0.3.5` tag — see `client::ui::tui_panel` in "Architecture") also carries a local fix, found and applied this session: upstream's `TerminalPlugin::build()` unconditionally registers its own `AssetLoader` for the `.ttf` extension (for `TuiFontSource::Asset`'s `AssetServer`-based font loading) — confirmed live, in both plugin-registration orders relative to `DefaultPlugins`, that this crashes `bevy_asset_loader`'s dynamic-asset system (this project's own `CommonAssets` font loading, completely unrelated to whichever `.ttf` path the panel itself uses) with a `TypeId`-mismatch panic at startup. Patched to drop just that loader registration (`bevy_plugin.rs`'s `LOCAL PATCH (prototype_19)` comment) — `TuiFontSource::Ready` (embedded/runtime bytes via `Font::new`/`Fonts::new`, bypassing `AssetServer` entirely) is unaffected and is what `tui_panel.rs` actually uses; `TuiFontSource::Asset` is unusable in this workspace as a result, worth knowing before reaching for it.

`bevy`, `avian3d` (physics), `bevy_skein`, `bevy_enhanced_input`, `bevy_asset_loader`, and `bevy_hanabi` (particles) are pulled from crates.io, but `[workspace.dependencies]` keeps commented-out `path = "../..."` lines for all of these too — if a registry release is broken or lags a needed feature, swapping to the sibling checkout is the established escape hatch.

`bevy_ahoy` (a Bevy + Avian + BEI kinematic character controller) is also from crates.io — 0.2.x is the release line matching this workspace's `bevy` 0.19 / `avian3d` 0.7 / `bevy_enhanced_input` 0.26 (0.0.x/0.1.x target older Bevy). No longer client-only as of M2: `shared` (the `player()` bundle + action-type registration) and `server` (the authoritative KCC) declare it too. `default-features = false` (set at the workspace entry, since a member can't override `default-features` on an inherited dep): the only default feature, `pickup`, would pull in `avian_pickup` and make `AhoyPlugins` auto-register `AvianPickupPlugin` + `AhoyPickupGluePlugin`, which nothing here wants yet. `AhoyPlugins` (the crate's plugin group — note the docs' usage example says `AhoyPlugin`, which doesn't exist in 0.2.0) is registered in **both binaries** — `client/src/main.rs` and `server/src/main.rs`'s nested GLTF tuple (headless-safe: `InputPlugin` disables BEI's raw-input systems on server-only builds). The KCC simulates the player on both sides over the same replicated-BEI input stream; the client's copy is the prediction.

`bevy_common_assets` (crates.io, `ron`+`toml` features only, `default-features = false`) is a separate dependency from `bevy_asset_loader` despite the similar name and close integration — it's a generic `Asset` loader for plain data files, whereas `bevy_asset_loader` is the collection/`LoadingState` machinery (`CommonAssets`, `PreloadCollection`, `LevelMetadataAssets`). **Correction to an earlier version of this doc**: it is *not* what loads `shared::assets::level::Level` — that has its own fully custom `AssetLoader` (`LevelAssetLoader`, registered via `SharedAssetsPlugin`), independent of `bevy_common_assets` entirely, because `model`/`skybox` need `LoadContext` access a generic `RonAssetPlugin` never gets. `bevy_common_assets` is pinned to whatever `0.17.0`-compatible version `bevy_asset_loader` itself pulls in transitively, since `bevy_asset_loader`'s own dynamic-asset manifests use this crate internally too — see the version-pin comment in `Cargo.toml` if bumping either one.

`chill_bevy_console` (crates.io) provides the in-game dev console (backtick to toggle) — see the console-gating convention below; it shapes how observers are registered throughout `client`.

Reflected types (e.g. anything Skein reads out of a `.glb`'s extras) are identified by Bevy's crate-qualified `TypePath`. Renaming a crate or moving a module changes that path — after the workspace split (crate renamed `prototype_19` → `client`), a previously-exported `.glb` had to be re-exported from Skein because its baked-in type references no longer matched. Expect this any time a crate/module housing reflected types gets renamed or moved.

## Architecture

`client/src/main.rs` is pure composition — a `Plugin` (`Prototype19`) listing feature plugins, plus the crate-root `add_observers_run_if!` macro (see conventions below). Modules are grouped into subdirectories — `controls/`, `dev/`, `gameplay/`, `lifecycle/`, `presentation/`, `ui/`, `assets/` — each with its own `mod.rs`; bullets below name the module, not its full path.

Game flow is a top-level state machine. `GameState` itself — along with `VRState`, `ServerState`, `ModalMenuState` — lives in `shared::game_state`, not a client-only module, since `ServerState` needs to be visible to `server` too; `GameStatePlugin` registers `GameState`/`VRState`/`ModalMenuState` (not `ServerState` — that's server-only, initialized in `server/src/main.rs`). `GameState` variants: `AssetLoading` (`#[default]`), `MainMenu`, `Lobby`, `Loading`, `Paused`, `InGame` — **`Loading` and `Paused` are dead variants**, confirmed via a full-workspace grep: nothing transitions to or checks for either anywhere (`Paused` survives as a name because the in-game pause menu is its own `ModalMenuState` machine, not a `GameState`). The real flow is driven by component add/remove observers, not a distinct loading state:

1. `Startup`: `spawn_client_link` creates the client's one persistent connection entity (`lifecycle::networking::ClientLink`).
2. The main menu's Connect button triggers `crate::events::Connect` → `on_connect_request` opens a real lightyear UDP/netcode connection (`client::NetcodeClient`, `Authentication::Manual`, hardcoded dev-only `PROTOCOL_ID`/`PRIVATE_KEY` matching the server's).
3. `On<Add, lightyear::prelude::Connected>` (`on_connected`) → `GameState::Lobby`.
4. The lobby's Play button sends `InGameRequest`; its level picker sends `LoadLevelRequest` — two independent actions (see `ui/lobby.rs` below). The server drives `ServerState` through `Loading`/`InGame` on the level side, and separately spawns a player character + inserts `ClientInGame` on the join side (see the "Server" section).
5. `On<Add, shared::replication::ClientInGame>`, gated on `Has<Controlled>` being true for that entity (`on_in_game`) → `GameState::InGame`. `On<Remove, Controlled>`, same gate (`on_out_of_game`) → back to `GameState::Lobby`.
6. `On<Add, lightyear::prelude::Disconnected>` (`on_disconnected`) → `GameState::MainMenu`, unless currently `AssetLoading` (guards against the very first frame, since `Disconnected` is a required component of `NetcodeClient` and fires once before any real connection attempt).

Most gameplay/UI entities are scoped to a state via `DespawnOnEnter`/`DespawnOnExit` so they self-clean on transitions instead of needing manual teardown systems. Three further independent state machines layer on top of `GameState`: `VRState` (`Desktop`/`VR`, set once at startup from `main.rs`'s VR bootstrap), `ModalMenuState` (`Closed`/`Open` — the in-game pause menu, `ui/modal_menu.rs`, overlaying `GameState::InGame` without replacing it), and `InputDeviceState` (`KeyboardMouse`/`Gamepad`, continuously updated from raw input events so UI like `hud.rs`'s control-tip icons can show the right device's glyphs).

Key modules:

- **`main.rs`** — beyond plain plugin composition, two decisions get made here that can't wait for a normal `Startup` system:
  - **VR/Desktop plugin choice**: reads `config.toml`'s `vr` field via plain `std::fs` *before* anything else runs, since which plugin group even gets added — `DefaultPlugins` vs. `add_xr_plugins(...)` — is a one-time choice that has to happen up front. Switching between desktop and VR needs a restart, same as most other desktop/VR-crossplatform games.
  - **Disabling client-side physics simulation**: the server is authoritative for physics, so the client only needs colliders and spatial queries (`SpatialQuery` raycasts/shapecasts — `targeting.rs`'s hover raycast), not to actually simulate anything. `PhysicsPlugins::default().build()` has `IntegratorPlugin`/`SolverPlugin`/`CcdPlugin`/`XpbdSolverPlugin` disabled — **not** `Time::<Physics>::pause()`, which would also stop broad/narrow-phase from running and leave spatial queries stale against moving colliders. Confirmed by testing to also fix a real physics glitch on reconnect that the client's own local solver fighting freshly-replicated `Transform` corrections used to cause. `PhysicsSchedule`'s `ambiguity_detection` is relaxed to `LogLevel::Warn` (several solver plugins being gone loses ordering guarantees for ~21 system pairs that would otherwise panic at schedule-build time — confirmed none of them are pairs this project's own systems actually race on) and `Gravity` is manually `init_resource`'d (normally `IntegratorPlugin`'s job). `SolverBodyPlugin`/`IslandPlugin`/`IslandSleepingPlugin` are explicitly *not* disabled despite the "solver" naming — disabling `SolverBodyPlugin` crashed the collider tree with an index-out-of-bounds panic, confirmed by testing.
  - **Client-side prediction is live since the ahoy migration's M0**: lightyear's `PredictionPlugin` runs *un-disabled* now — it used to panic (`"Resource does not exist: LastConfirmedInput"`) because it assumes one of lightyear's own input-replication plugins (`lightyear_inputs_native`/`_bei`/`_leafwing`) has already run, and none of those were depended on back when `Movement`/`Jump` were plain `MessageSender` messages. M0 resolved that the idiomatic way: `lightyear_inputs_bei` (BEI is ahoy's native input layer) registers the needed state via `shared::inputs::SharedInputsPlugin`, so the plugin runs as part of `client::ClientPlugins` — see the comment in `main.rs` if touching this area.
- **`gameplay/player_character.rs`** — the client never spawns its own player character; the server does (`server::networking::in_game_request`) and it arrives here via replication, as a *separate* entity from the connection (see the top-of-file architecture-change note). `on_player_spawned` — despite the name, a **polling `Update` system, not an observer** (`Query<Entity, (With<PlayerCharacter>, Added<Controlled>)>`, deliberately, since replication's initial full-state sync on a late join doesn't reliably fire per-component `Add` observers the way a live mid-session insert does) — finds the local client's own character via `lightyear::prelude::Controlled` (inserted client-side only on the entity this client actually owns, as a side effect of `ControlledBy`/`ControlledSend` replicating correctly) and sets `LocalPlayer(Some(entity))`, then decorates that entity with `controls::player_controls()`, the FPS camera rig, etc. `decorate_other_players` (a separate polling system) gives every *other* `PlayerCharacter` a visible model. `LocalPlayer(pub Option<Entity>)` is the resource other modules (`targeting.rs`, `hud.rs`) read to know "which replicated entity is mine."
- **`controls/actions.rs`** — every `bevy_enhanced_input` `#[derive(InputAction)]` marker struct for the player, all in one file rather than defined near each handler.
- **`controls/controls.rs`** — owns the player's entire input surface. Since the ahoy migration (M2–M4) its two halves are: `bind_replicated_ahoy_actions` (the **polling** `Update` system that binds real inputs to the server-spawned replicated ahoy action entities — the M2 input flow; movement/jump/look have no message handlers at all anymore, the replicated BEI stream *is* the transport) and the remaining message-sending hotkey observers — `attack`/`kill` send `AttackAttempt`/`KillAttempt` via `MessageSender<T>::send::<OrderedReliable>(...)` (lightyear's API — **not** `commands.client_trigger(...)`, which was the old `bevy_replicon`-era shape and no longer exists in this codebase); `shoot`/`spawn_npc` route through one extra client-local event (`SpawnCube`/`SpawnNpc`) before crossing the network via the same `MessageSender` mechanism; `rotate_camera` (on the ahoy `RotateCamera` action) drives the client camera from the same replicated action values the server's look accumulator consumes. `AttackAttempt`/`KillAttempt` each carry one `Entity` field, but it's the *target*, not the attacker — the server resolves who's acting from the sending connection, same as the spawn requests. **`return_to_main_menu` is fixed** — see the top-of-file gap note; Escape/pause-menu-"Main Menu" both work now. Also registers `TargetingPlugin`.
- **`events.rs`** — client-local events with no server-authoritative meaning: animation triggers, `Play` (see `ui/lobby.rs`'s bullet for a possible overlap worth checking), and the `SpawnCube`/`SpawnNpc` client-input triggers.
- **`lifecycle/networking.rs`** — opens the client's UDP/netcode connection (`SERVER_PORT = 6000`, address config-driven, `PROTOCOL_ID`/`PRIVATE_KEY` hardcoded dev-only values that must match the server's exactly) and drives every `GameState` transition described above (`on_connected`, `on_disconnected`, `on_in_game`, `on_out_of_game`). `ServerAddress(pub String)` defaults to `"127.0.0.1"`, overwritten by `config.toml`'s `server_ip` at `Startup`. `ClientLink(Entity)` is the one persistent connection entity reused across every connect attempt (including reconnects) — every system needing "my own connection" (`Single<&mut MessageSender<T>>` queries throughout `controls.rs`/`ui/lobby.rs`) relies on there being exactly one. `on_disconnect_request` deliberately triggers **both** lightyear's `Disconnect` and `Unlink` — triggering only `Disconnect` left a stale `Linked` marker that caused a real `Option::unwrap()` panic in `lightyear_udp` on a subsequent reconnect, confirmed by testing.
- **`lifecycle/lobby.rs`** — `OnEnter(GameState::Lobby)` spawns the lobby UI (`ui/lobby.rs`'s `lobby_ui`) and its own `MenuControls` input-context entity. Also registers `sync_level_options`/`apply_selected_level` (defined in `ui/lobby.rs`) and an `on_play` observer that sends `LoadLevelRequest` for a hardcoded `"levels/spawn.level.ron"` in reaction to the `Play` client-local event — **worth checking whether this overlaps with or is superseded by** `ui/lobby.rs`'s `lobby_play_button`, which sends `InGameRequest` directly (a different message) on the same "Play" button; these look like two independent paths that may not both still be meaningfully wired to UI, not confirmed which (if either) is dead.
- **`ui/lobby.rs`** — the actual lobby UI: three buttons under a `lobby_background` `WorldAssetRoot` — Play (`lobby_play_button`, sends `InGameRequest`), a level picker (`level_picker()`, built on `selector.rs` — see below, populated from the server-replicated `shared::level::Levels` singleton, resolving each `Level::name` `.ftl` key via `bevy_fluent::Localization::content` with a raw-key fallback), and Main Menu (disconnects, returns to `GameState::MainMenu`). Picking a level sends `LoadLevelRequest { asset_path }` directly (`apply_selected_level`), reacting to `selector::UiSelected` the same pattern `ui.rs`'s language/options pickers use.
- **`ui/selector.rs`** — a generic, reusable paginated "selector" popup widget (5 visible rows, `SELECTOR_VISIBLE_ROWS`): gamepad/keyboard/mouse-wheel navigation, a discrete scrollbar, `AutoDirectionalNavigation` locked to the popup while open, firing `UiSelected { entity }` when a row is chosen rather than baking in any one domain's selection logic — a consumer reads whatever payload component its own `SelectorOption::payload` closure inserted onto the chosen slot entity. Used by `ui/lobby.rs`'s level picker and `ui.rs`'s language/options pickers. ## Server (`server/src/`)

Headless — `MinimalPlugins`, not `DefaultPlugins` — which means anything `DefaultPlugins` normally gives you for free has to be added or registered explicitly: `StatesPlugin` (needed for lightyear's own states, and this project's `ServerState`) and `bevy::log::LogPlugin` are added directly; `.init_asset::<Mesh>()`/`.init_asset::<Image>()` are called manually; and `server/Cargo.toml`'s `bevy` dependency explicitly enables `reflect_auto_register` (needed because `bevy_world_serialization`'s spawner reflects every component, including builtins like `Transform`, onto instantiated entities and panics if a type is missing from `AppTypeRegistry` — the client gets this for free through `default-features = true`, the headless server doesn't). Files: `main.rs`, `networking.rs`, `rooms.rs`, `lobby.rs`, `level_state.rs`, `combat.rs`, `spawn.rs`, `tools.rs`, `replay.rs` — no submodule directories, all declared inline in `main.rs`.

- **`main.rs`** — pure composition. **`AssetPlugin`'s `file_path` override to `client/assets` is now commented out** — the server uses its own default asset root, `server/assets/` (confirmed to exist: `server/assets/levels/{spawn,outpost,minimal}.level.ron`, `server/assets/rigs/{environment/*.glb, minimal_level.glb, armature/npc.glb, prop/cube.glb, skin/npc.glb}`). An earlier version of this doc (and a stale doc comment still in `main.rs` itself) described the server as having no `assets/` of its own and pointing at `client/assets/` — that's no longer true; don't trust that specific comment over the actual (commented-out) code. Full plugin list, in order: `MinimalPlugins`, `StatesPlugin`, `LogPlugin`, `TransformPlugin`, `AssetPlugin` (see above), `PhysicsPlugins` (same config as the client: `PhysicsTransformPlugin`/`PhysicsInterpolationPlugin` disabled — `LightyearAvianPlugin` owns `Position`/`Rotation`↔`Transform` sync, and `sync_to_transform: true` — see the ahoy migration's findings in the top-of-file gap note), `server::ServerPlugins { tick_duration: 1/60s }`, `LightyearAvianPlugin { replication_mode: AvianReplicationMode::Position { sync_to_transform: true } }`, `SharedReplicationPlugin`, `SharedAssetsPlugin`, `SharedInputsPlugin`, `ServerCombatPlugin`, `ServerSpawnPlugin`, a nested tuple of `(GltfPlugin, WorldSerializationPlugin, SkeinPlugin, AhoyPlugins, ServerInputPlugin, LevelStatePlugin, GameRoomPlugin, LobbyPlugin)` (nested purely to stay under `add_plugins`'s tuple-arity limit — the outer tuple is at Bevy's 15-element `Plugins` limit — not because they're related), and `networking::NetworkingPlugin`. No `bevy_quinnet`-style `ConnectionLostEvent`/`NetworkIdMap` lookups anywhere in this codebase anymore.

- **`spawn.rs`** — `ServerSpawnPlugin`: `spawn_npc`/`spawn_cube`, both gated on a per-caster `Gcd` cooldown, spawning `(npc(...)/cube(...), Replicate::to_clients(NetworkTarget::All), Selectable)` — **standalone entities, no `ChildOf` parent, no `Rooms` tag** (unlike the level geometry and player characters) — see the top-of-file gap note. **Live bug (see the top-of-file caster-resolution gap)**: both systems look the caster's `Gcd` up *on the connection entity* (`casters.get_mut(entity)`) — which has none since the player became a separate entity — so every spawn request is silently dropped at the `Err`→`continue` guard and nothing spawns, for human hotkeys and agent triggers alike. Fix: resolve the connection's player character (via `ControlledBy { owner }`) and read the `Gcd` from it. `spawn_npc` does a real `SpatialQuery::shape_intersections` clip-check before spawning (skips if it would overlap geometry); `spawn_cube`'s equivalent check has its `continue` commented out — **deliberately**, matching this project's established "cube-stacking is a mechanic, not a bug" design (unchanged from before the lightyear migration) — don't "fix" that to match `spawn_npc`.
- **`tools.rs`** (new file, not previously documented here) — a server-side BRP+MCP debug surface mirroring the client's `dev::tool_api` (ADR 0009/0010 pattern): always compiled in (no feature gate — the server is trusted), BRP on **15701**, MCP on **15711** (`--brp-port`/`--mcp-port` override). One method, `server/state`, dumps authoritative app state, every connected client, and every live player's server-side transform/HP/owning connection — built for comparing against a client's own (predicted, room-filtered) view when debugging desync. Registering its unconditional `RemotePlugin` add used to collide with `bevy_skein::SkeinPlugin`'s own debug-mode default (`handle_brp: cfg!(debug_assertions)`) and crash every debug-profile server at startup — see the gap-list's "Fixed: debug builds of `server` panicked" bullet; `main.rs`'s `SkeinPlugin` now sets `handle_brp: false` to match.
- **`replay.rs`** — session recording (`ReplayRecorderPlugin`, always registered, no-ops unless `SERVER_REPLAY_RECORD` is set) + deterministic debug-replay (`run_replay`, entered via `main.rs`'s `--replay <path>` dispatch instead of the live `.run()`) — see the gap-list's "Added: `server::replay`" entry for the full mechanism, its `ActionMock`-doesn't-work-server-side finding, and its known open movement-rate discrepancy. `main.rs`'s plugin registration was refactored into `pub(crate) fn build_app(networking_plugin: impl Plugins<M>) -> App` specifically so both the live path (`build_app(networking::NetworkingPlugin)`) and replay (`build_app((networking::NetworkingPlugin, replay::ReplayPlaybackPlugin { events }))`) share every other plugin/schedule-executor/asset-registration line verbatim — replay's own `run_replay` still includes the real `NetworkingPlugin` (confirmed live: omitting it panics, `lightyear_replication::server::receive_server_packets` depends on a resource only `NetworkingPlugin`'s `Startup` bootstrap inserts) even though it never receives real packets.

## Notable conventions

- Interaction/selection targeting uses a raycast against `Selectable`-tagged entities each frame (`targeting::raycast_from_center`), writing into `Hovered`/`Selected` — the hub to touch when changing targeting behavior.
- Input is entirely `bevy_enhanced_input`: actions are marker structs (`#[derive(InputAction)]`), all defined together in `client/src/controls/actions.rs` — deliberately *not* near each handler — bound together in `controls.rs`'s single `Actions::<PlayerControls>::spawn` block, handled via observers (`On<Fire<T>>`, `On<Start<T>>`, `On<Complete<T>>`).
- **Component lifecycle observers are used liberally as a state-machine mechanism**, not just for setup/teardown: `On<Add, T>`/`On<Remove, T>` drive real gameplay reactions (e.g. `Idle`, `Grounded` transitions feeding the animation system, or `ClientInGame`/`Controlled` driving `GameState` transitions client-side), not just cleanup. Prefer this over a polling `Update` system with a manual guard/marker component when what you're reacting to might legitimately land on a *different* entity or at an unpredictable *later* time than "setup time" — that's exactly the shape of bug a polling+guard system produces silently. The flip side, equally real: a few systems (`client::gameplay::player_character`'s `on_player_spawned`, `client::combat`'s `hide_dead`) are deliberately polling `Update` systems *instead of* observers, because replication's initial full-state sync on a late join or reconnect doesn't reliably fire per-component `Add` observers the way a live mid-session insert does — confirmed by testing in both cases, not assumed. Don't "fix" either direction without re-testing the specific path (fresh connect vs. reconnect vs. late join) that motivated it.
- **`EntityEvent` vs plain `Event`**: reach for `#[derive(EntityEvent)]` (a field literally named `entity`, or `#[event_target]` on another field) when you want `commands.entity(e).observe(...)` scoping or propagation. It only supports *one* formal target per event — for a two-entity relationship (e.g. `shared::server_events::Attack`'s `entity`/`attacker`), put the side you want scoped-observe on as `entity`, and the other as a plain field.
- Cross-cutting gameplay events are Bevy observers/triggers (`commands.trigger(...)`), not plain systems reading queues.
- **Server never trusts a client-supplied entity for "who sent this"** — resolve identity from the connection entity a `MessageReceiver<T>` component lives on (the `Entity` half of a `Query<(Entity, &mut MessageReceiver<T>)>`), never from anything in the message payload. `movement`/`jump`/`resolve_attack`/`resolve_kill` all follow this — the latter two do still read an `Entity` out of the payload (`AttackAttempt`/`KillAttempt`'s `entity` field), but only to say who the action *targets*, never who's performing it. (An earlier version of this doc described this via `bevy_replicon`'s `On<FromClient<T>>`/`ClientId::Client(entity)` API — that API no longer exists in this codebase at all; the pattern itself is unchanged, only the mechanics of *how* identity is resolved changed with the lightyear migration.) The same logic applies in reverse for entity-mapped messages: any message carrying an `Entity` needs `#[entities]` on that field plus `#[derive(MapEntities)]`, and must be registered via `.register_message::<T>().add_direction(...).add_map_entities()` (not omitting the last call) — the mapping only resolves correctly for entities that are themselves replicated.
- **Console-gating**: gameplay observers that shouldn't fire while the dev console is open are registered through the crate-root `add_observers_run_if!` macro (`main.rs`, `pub(crate) use`d) with `chill_bevy_console::console_closed` as the condition. Lifecycle/cleanup observers are registered as plain, ungated `app.add_observer(...)` instead — gating a spawn reaction like this was a real bug once (opening the console before a one-shot spawn trigger fires silently drops it forever, since observer triggers aren't queued/retried). Lifecycle/spawn handlers must stay ungated; only "please do X now" player-input actions should be gated.
- Hierarchy walks reuse `Query<&Children>::iter_descendants`/`iter_descendants_depth_first` and `Query<&ChildOf>::iter_ancestors`/`root_ancestor` (inherent `Query` methods, no extra trait import) rather than hand-rolled recursion.
- **Room-based interest management** (`lightyear_replication::visibility::room`, see the "Server" section's `rooms.rs`/`lobby.rs` bullets): a `Rooms` component on an entity, and a matching `Rooms` component on a client's own connection entity, is what makes that entity actually replicate to that client — sharing at least one `RoomId` is required, not optional; an entity with no `Rooms` component at all bypasses room filtering entirely and replicates to every client its `Replicate`/`NetworkTarget` otherwise allows (this is *why* cubes/NPCs currently leak across rooms — see the top-of-file gap note). `Rooms::single(id)` *replaces* a component's entire room membership, it doesn't add to whatever was there before — inserting it on an already-room-tagged entity (e.g. a client moving from the lobby room to the game room) is how "leave the old room, join the new one" is expressed, not two separate calls. Room membership on a piece of *content* and room membership on a *watching client* are two independent things that both need setting — tagging content with a room does nothing for a client that isn't itself a member of that same room, and vice versa (this exact gap — updating an entity's room but forgetting the connecting client's own room membership — was a real bug hit while building this).
