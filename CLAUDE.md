# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Bevy 0.19 (Rust, edition 2024) 3D game prototype. **Cargo workspace** with three members: `client` (the playable game — rendering, UI, input, camera, presentation), `server` (a real headless authoritative simulation server — physics, level loading, player spawning, movement/combat resolution), and `shared` (the simulation logic and network-message types both sides need to agree on: character controller, combat, player bundle, spawners, replication registration). No tests currently exist in the repo.

The workspace was built in anticipation of an "always multiplayer" architecture — even singleplayer would run a local client *and* server, simulation on the server / presentation on the client, so hosting real multiplayer later is "open a port" rather than a rewrite. That split is now real, not just plumbing: `server` is authoritative for level geometry (loads and instantiates `.glb` files headlessly, generates real Avian colliders — see the "Server" section below), player spawning (a client's own connection entity doubles as its player character — see `server::networking`), and movement/combat resolution (`shared::character_controller`, `shared::combat`). `client` sends intent as network events (`Movement`, `Jump`, `AttackAttempt`, ...) and renders whatever the server replicates back; it does not decide outcomes. `bevy_replicon`/`bevy_replicon_quinnet` (QUIC transport) are real, load-bearing dependencies now, not scaffolding — see `shared::replication::SharedReplicationPlugin` for the full list of replicated components and client/server events. `bevy_asset_loader` is now a real, load-bearing dependency too (no longer unused) — `client::assets::collections::CommonAssets` is the client's actual asset manifest, loaded through a `LoadingState` scoped to `GameState::AssetLoading` before the app ever reaches `MainMenu` (see the `assets` module bullet below). `bevy_common_assets`' `RonAssetPlugin` loads plain `.ron` data assets (e.g. per-level manifests) alongside it.

What's still genuinely missing, worth not assuming exists: client-side prediction (every input round-trips through the server before it's visible — fine on loopback, will feel laggy over real latency); cleanup of a disconnecting client's non-connection-entity `Replicated` entities; and despawning the previous level's server-side geometry on reload — the server still never despawns a `LevelRoot`/`WorldAssetRoot` once loaded (see `server::level_state::LevelState`'s doc comment and the "Server" section's `networking.rs` bullet), it just now *rejects* any further `LoadLevelRequest` while one is already loading/loaded rather than spawning a second one on top of it, which is a narrower fix than actual level-switching support. One more open question, not yet resolved either way: once a character's `HitPoints` hit zero it's marked `Dead` (see `server::combat`) rather than despawned immediately, but nothing currently stops a dead player from still moving/attacking during that window — `on_movement`/`on_jump`/`resolve_attack`/`resolve_kill` don't check for `Dead`. Worth deciding whether that's acceptable before relying on it. (`AttackAttempt`/`KillAttempt` resolving *identity* from a client-supplied `Entity` used to be listed here as a known gap — it isn't one any more: `resolve_attack`/`resolve_kill` both resolve `attacker`/`killer` from `attempt.client_id`, same as `Movement`/`Jump`. See the `ClientId`-resolution convention below.)

## Platform targets

Steam Deck is the primary/min-spec target, not a secondary port — most of the realistic install base (Deck itself, other handhelds, gaming laptops, older desktops) is roughly Deck-class hardware, and tuning for a fixed console-like spec first is an easier bar to hit reliably than an unbounded PC hardware matrix. A higher-end PC gets a fidelity bump (heavier AA, higher shadow/texture resolution, larger draw distance), not different content — what actually exists in the world at a given position must stay identical across hardware, since this is a multiplayer game and letting quality settings change *what's loaded*, not just how it's rendered, would desync what different players in the same session can see/interact with.

The concrete number this is designed against is Deck's ~4GB VRAM budget — already a real constraint the asset pipeline is built around, not a future concern:
- The KTX2-compressed-texture and BC6H-compressed-skybox pipelines (`scripts/hdri_to_skybox.py`, `glbpack.sh`) already cut real assets 3-4x smaller on disk and in VRAM, confirmed by direct measurement (e.g. one skybox: 192→24 MiB VRAM).
- The scaling model this points toward: a texture-quality setting resolves the *same* `#[asset(key = "...")]` keys `CommonAssets`/`PreloadCollection` already use against different source directories or mip-stripped KTX2 variants (1K/2K on Deck, 2K/4K on a high-end PC) — the streaming/proximity-loading logic stays quality-tier-agnostic, only the manifest paths and the VRAM-budget number it's checked against change.
- `PreloadCollection`/`PreloadBeacon` (see the `assets/` bullet below) exist specifically to keep total resident VRAM under budget on Deck by only keeping nearby content loaded — not purely a pop-in/loading-screen concern, a genuine memory-pressure mechanism a beefier PC target wouldn't strictly need but benefits from anyway (it's what lets a bump to 4K textures stay affordable at all, by capping how much can be resident simultaneously).

Also relevant to "Deck Verified" specifically: `input_icons.rs`/`hud.rs`'s `controls_tips` already render real Steam Deck button glyphs (`steam_deck_atlas_image`/`_manifest` in `CommonAssets`), and the existing gamepad-first UI navigation (`ui.rs`'s `menu_controls`, `MenuControls` input context) covers Valve's "default controls work" verification criterion without extra work — worth keeping in mind before assuming any Deck-specific UI/input work is still outstanding.

## Character authoring pipeline (design direction — mostly not implemented yet)

The goal is one data-driven, unified spawning system used identically for the player, NPCs, and eventually AI-driven enemies — several independently-authorable, independently-reusable axes per character, rather than a bespoke hand-built bundle per character type (`shared::player::player()`'s current hardcoded `PLAYER_*` constants are exactly what this is meant to eventually replace, though nothing has been migrated off it yet). The axes, deliberately kept orthogonal so any one can be swapped or reused without touching the others:

- **Rig** (`assets/rigs/*.glb`, presumably split under `character`/`environment`/`prop` per the existing directory convention) — bones, animations, and Skein-authored gameplay markers: a bare `RigRoot` marker component (`assets::character::RigRoot`, no fields) on the armature's root empty, plus (not yet built) weapon/gear attachment-point empties, hit-registration collider empties, and a camera pivot. Deliberately excludes the visible mesh/materials — those live in a separate **skin** `.glb`, meant to be spawned as a swappable child so re-skinning a character doesn't touch its rig/gameplay setup. Not yet implemented, and genuinely nontrivial when it is: glTF skinning binds a mesh's joints to `Entity` indices within its *own* export, so an independently-exported skin `.glb` brings its own redundant copy of the bone hierarchy by default. Sharing the armature's live animated pose needs the skin's `SkinnedMesh.joints` re-targeted at spawn time to the armature's already-instantiated bones (matched by name), not just parented as a child — the same "find a named entity inside an already-instantiated rig" primitive that weapon/gear attachment points and the camera pivot will also need, worth building once as shared infrastructure rather than three times.
- **Controller** (`assets::controller::Controller`, `.controller.ron`, loaded via `RonAssetPlugin` registered in `main.rs`) — pure movement-feel data: `collider`/`ground_detection_collider` (`ColliderConstructor`), `acceleration`/`damping`/`jump_impulse`/`gravity`/`terminal_velocity`, `ground_detection_max_angle`/`max_distance`, `game_layer`. `assets/controllers/player.controller.ron` mirrors `shared::player::player()`'s current hardcoded values exactly, but nothing loads or applies it yet. Conclusion reached while designing this: nearly every character — player, NPCs, animals, robots — reduces to the same `MoveAndSlide` shape (one capsule/cylinder collider regardless of visual complexity; legs/wings/whatever are an animation-layer concern, not a collision one). The only real algorithmic outlier found is wheeled vehicles (raycast/suspension simulation, not a capsule sweep); earlier "mount"/"quadruped controller type" ideas turned out to just need different `Controller` *data*, not a different algorithm — so a `Controller` variant enum, if it ever grows one, likely only ever needs `MoveAndSlide` and `Vehicle`.
- **Stats** (`assets::stats::Stats`, `.stats.ron`, not yet registered as loadable) — RPG numbers (`vitality`/`strength`/`agility`/`intellect`/`luck`, plus whatever else accumulates). Deliberately meant to apply identically to the player and every NPC, not a player-only system — the design reasoning: if the player and every enemy are governed by the same stat/damage math, skill and system-knowledge the player builds against enemies genuinely transfers to reasoning about their own character, the way Dark Souls-style games are often praised for feeling fair even when difficult. `shared::combat.rs`'s current `DAMAGE`/`ATTACK_RANGE` are flat global constants applied to every attack regardless of attacker — `Stats` is meant to replace that with real per-character values, which needs `server::combat::resolve_attack`/`resolve_kill` to actually read a `Stats` component rather than a shared constant, a real behavior change, not just moving numbers into a file.
- **Abilities** — not yet stubbed in code at all. The intent is a shared "ability grammar" (cooldown, range, damage/effect shape, animation/VFX hooks) that both the player's hotbar (`hud.rs`) and an NPC's AI-selected action draw from the same asset pool, rather than bespoke Rust per ability. `shared::combat::Gcd` (the existing shared global-cooldown component) is a working precedent this would extend, not a new pattern.
- **`Character`** (`assets::character::Character`, `.character.ron`, e.g. `assets/characters/player.character.ron`) — the aggregation point: `rig`/`controller`/`stats` fields, each a bare `AssetServer` path, *not* an id looked up through a manifest file. A `manifest.toml`-style id→path indirection was tried first (`client/assets/controllers/manifest.toml`, now stale/unused) and deliberately dropped: it's a second file that can silently drift from the paths it's supposed to index — the same category of bug the `PreloadBeacon`/`preload_collections` divergence problem (see the asset-streaming design further down) was built to eliminate. Pasting a literal asset path into Skein's data panel has no such failure mode. Whatever eventually resolves a `Character` into a real spawned entity (not implemented yet) is expected to spawn `rig`, wait for `WorldInstanceReady` (the same readiness signal `loading.rs`'s level-spawn flow already uses, so a scene finishing *async* isn't mistaken for ready), find the `RigRoot`-tagged descendant, and insert the components resolved from `Controller`/`Stats` directly — done sequentially in the spawning system itself rather than as a separate reactive observer, since by that point the spawning code already has everything it needs and there's nothing left to rediscover.

Two existing systems are worth knowing aren't symmetric between player and AI yet, since making them so is exactly what this design is for:
- `shared::character_controller`'s `MovementInput`/`JumpInput` already are — plain server-local `EntityEvent`s, not network-request types, so a nav-mesh/steering system could trigger them directly for an NPC today, exactly like `controls.rs` does for the player, with no `ClientId` resolution needed at all (there's no client to distrust for an NPC-originated action). `polyanya`/`rerecast` (vendored navmesh pathfinding/generation, see Dependency layout) are the not-yet-wired pieces an AI steering system would connect through this path.
- Combat is *not* symmetric yet: `AttackAttempt`/`KillAttempt` are `shared::client_events` types, and `resolve_attack`/`resolve_kill` are observers scoped specifically to `On<FromClient<AttackAttempt>>`/`On<FromClient<KillAttempt>>` — today only a real connected network client can trigger an attack, there's no path in for AI at all. Closing that needs the same shape of fix as movement: extract the actual resolution logic so it's reachable both from a real client's `FromClient<T>` and directly, with no network hop, from a server-side AI decision.

Worth knowing this design converges with, not diverges from, how commercial engines actually do this at scale — not a coincidence, the same production pressures (many characters, many designers, live tuning without recompiling) push toward the same shape: Unreal's `CharacterMovementComponent` drives player- and AI-controlled pawns through the identical component for the identical reason as the `Controller`/AI-reuse design above; Unreal's Gameplay Ability System (`AttributeSet`/`GameplayAbility`/`GameplayEffect`) is a shipped, commercial answer to exactly the "one system, used identically for player and NPCs" goal behind `Stats`/abilities here. Unity's `CharacterController` component plus `ScriptableObject` data assets are the same shape at the movement/data-externalization layer. The one real gap versus those engines: no visual/GUI editor for any of this — `Controller`/`Character`/`Stats` are hand-authored RON text files, which is a real production-ergonomics tradeoff for a larger team, offset by being trivially diffable/merge-friendly in a way binary serialized asset formats usually aren't.

**Current implementation status**, to avoid a future session assuming more of this is built than actually is: only the `Controller`/`Character`/`Stats` struct definitions and their example `.ron` files exist. `RonAssetPlugin::<Controller>` is registered in `main.rs`; `Character`/`Stats` are not yet registered as loadable assets. Nothing resolves a `Character`/`RigRoot` into spawned components — `shared::player::player()` is still completely independent of all of this. Abilities have no code at all yet, not even a struct. The armature/skin split, attachment points, hit colliders, and camera pivot are pure design, nothing authored or spawned.

## Commands

```sh
cargo build -p client --release   # build of the game
cargo build -p server --release   # build of the server
cargo build --workspace --release # build everything
cargo run -p client --release     # run the game (connects once Play is pressed, not on startup — see config.toml below for the address)
cargo run -p server --release     # run the authoritative headless server (listens on 0.0.0.0:6000)
cargo check --workspace           # fastest way to verify compile errors across all members
cargo clippy --workspace
```

There is no test suite. Run commands from the workspace root (`prototype_19/`) — Bevy's default asset resolution is relative to each crate's own `CARGO_MANIFEST_DIR` at compile time, not the process's CWD, which is why `assets/` lives inside `client/` (`client/assets/`) rather than at the workspace root; moving it back out will break asset loading. `assets_src/` (raw `.blend` files and downloaded source-asset packs, exported/processed into `client/assets/` for actual runtime use — nothing loads from it directly) lives at the workspace root instead, alongside `client/`/`server`/`shared`, not inside `client/`.

`../build.sh` (one level up, outside this workspace) cross-builds a release binary inside a `steamrt-sniper` podman container for Steam Runtime compatibility. It runs `cd prototype_19 && cargo build --release`, which now builds the whole workspace — any packaging step downstream that expects a binary literally named `prototype_19` needs updating to `client`/`server`.

For testing inside the `steamrt4` toolbox (a lighter-weight alternative to `../build.sh`'s podman container — see `steam_deck_toolbox.sh`) or copying a binary to an actual Steam Deck: **always build with `./steam_deck_toolbox.sh cargo build -p <client|server> --release`** (or `toolbox run -c steamrt4 -- cargo build ...` directly — the script is just a thin wrapper around that; run bare with no args, it enters the toolbox interactively instead), never a plain host-side `cargo build`/`cargo run` for a binary that's going to run inside the toolbox or on the Deck. The toolbox and host share the same `rustc`/`cargo` toolchain via the bind-mounted home directory, so cargo's own fingerprinting genuinely cannot tell the two environments apart and won't force a relink on its own — a host build silently produces a binary linked against the host's (newer) glibc, which then fails on the toolbox's or Deck's older glibc with `GLIBC_2.4x not found` errors, even though nothing about the *build* looks wrong from the host's side. Recovering from this needs `cargo clean -p <crate> --release` before rebuilding inside the toolbox — deleting just the final binary isn't enough, since cargo can still decide only a relink (not a full recompile) is needed and reuse the host-tainted intermediate objects. Verify with `objdump -T target/release/<bin> | grep -oE 'GLIBC_[0-9.]+' | sort -Vu | tail -5` — a toolbox-built binary should top out around `GLIBC_2.39`, well under the toolbox's/Deck's actual baseline (`2.41` as of this container image), not `2.43`/`2.44`.

Tracy profiling (`cargo run -p client --release --features tracy`) is **opt-in**, not part of any default feature set — see `client/Cargo.toml`'s comment on the `tracy` feature. `bevy/trace_tracy` makes `tracy-client` buffer every instrumented span in memory until an actual Tracy GUI connects and drains it; with the feature always-on, a normal play session with no Tracy attached was a real incident (`cargo run -p client --release` ran RSS from ~9GiB to 40+GiB in under 4 minutes at ~150MB/s). Only build with `--features tracy` when you intend to actually attach Tracy and keep it attached for the run. The workspace root's `[profile.release] debug = true` (in `Cargo.toml`) exists so Tracy shows real function names instead of addresses — it applies to `server` too (harmless there, just a bigger binary) since Cargo profiles aren't per-member.

`client/assets/config.toml` (`server_ip`, `vr` — see `client/src/config.rs`'s `ClientConfig`, moved out of `networking.rs` into its own file) is the only way to point the client at a non-default server address or VR mode; there's no in-game UI for either (the main menu used to have a player-name/IP text field, removed in favor of this file). Both fields fall back gracefully if the file is missing or absent — `vr` defaults to `false` (`#[serde(default)]`), `server_ip` falls back to `"127.0.0.1"` — so a missing or partial `config.toml` degrades rather than fails to start. There's no `level` field any more — which level to load is now driven by the `Level`/manifest asset system (see the `assets` module bullet below), not a config file default.

## Dependency layout

Root `Cargo.toml` is the workspace manifest: `[workspace.package]` for shared `edition`/`version`, `[workspace.dependencies]` centralizing every dependency's version (or local path) in one place. Member `Cargo.toml`s reference them via `dep.workspace = true` rather than redeclaring versions. Two things worth knowing if you touch this:
- A member **cannot** override `default-features` on a `dep.workspace = true` reference, even if the workspace entry explicitly sets `default-features = true`. `server`/`shared` need a smaller `bevy` feature set than `client` (headless, no rendering), so they declare `bevy` directly with their own `default-features = false` instead of inheriting it — see `server/Cargo.toml`/`shared/Cargo.toml`.
- Path dependencies in `[workspace.dependencies]` resolve relative to the **workspace root** (where the root `Cargo.toml` lives), not relative to whichever member references them. The workspace root is at the same location the old single-crate root used to be, so these paths are unchanged from before the workspace split (`../bevy_mod_outline`, etc. — not `../../`).

Several dependencies are **not** pulled from crates.io — they're path-dependencies on sibling checkouts one directory up from the workspace root (`../<crate>`), i.e. forked/vendored versions of these libraries:

- `polyanya` (`../polyanya`) — navmesh pathfinding
- `rerecast` (`../rerecast/crates/rerecast`) — navmesh generation
- `bevy_mod_outline` (`../bevy_mod_outline`) — selection/hover outlines
- `bevy_vello` (`../bevy_vello`) — vector graphics rendering
- `bevy_seedling` (`../bevy_seedling`) — audio
- `audionimbus` (`../audionimbus/audionimbus`) — spatial audio

If something doesn't behave like upstream docs suggest, or a symbol can't be found, check the sibling checkout's source directly rather than assuming crates.io behavior — these may be patched/ahead-of/behind the published versions. `bevy_mod_outline` in particular carries a local fix: `pipeline_key.rs`'s `DerivedPipelineKey::new` used to force `motion_vector_prepass` to `false` for the `Stencil`/`FloodInit` pass types regardless of the view's actual state, which crashed (wgpu bind-group-layout validation error) when outlining a skinned mesh with `TemporalAntiAliasing` enabled. Fixed by letting them inherit the view's real flag like the `Volume` pass type already did. Worth upstreaming; if this crate is ever re-vendored, check whether the fix needs reapplying.

`bevy_oxr` (`../bevy_oxr`, providing `bevy_mod_openxr`/`bevy_mod_xr`/`bevy_xr_utils` — see the VR/OpenXR paragraph below) carries a similar local fix: `bevy_xr_utils::tracking_utils::TrackingUtilitiesPlugin`'s controller-grip tracking creates and attaches `left_pose`/`right_pose` OpenXR actions but upstream never actually suggests bindings for them (`app.add_systems(OxrSendActionBindings, suggest_action_bindings)` was commented out in `crates/bevy_xr_utils/src/tracking_utils.rs`), so the action spaces never locate to a real controller pose — both `XrTrackedLeftGrip`/`XrTrackedRightGrip` entities stay at the same untracked identity transform, which looked like "one box, no tracking" when first tried. Fixed by uncommenting that line (and importing `OxrSendActionBindings` from `bevy_mod_openxr::action_binding`). Also worth upstreaming; check whether it needs reapplying if this crate is re-vendored.

`bevy`, `avian3d` (physics), `bevy_skein`, `bevy_enhanced_input`, `bevy_asset_loader`, and `bevy_hanabi` (particles) are pulled from crates.io, but `[workspace.dependencies]` keeps commented-out `path = "../..."` lines for all of these too — if a registry release is broken or lags a needed feature, swapping to the sibling checkout is the established escape hatch.

`bevy_common_assets` (crates.io, `ron`+`toml` features only, `default-features = false`) is a separate dependency from `bevy_asset_loader` despite the similar name and close integration — it's a generic `Asset` loader for plain data files (`RonAssetPlugin::<T>`, used by `client::assets::level::Level`), whereas `bevy_asset_loader` is the collection/`LoadingState` machinery (`CommonAssets`, `PreloadCollection`). Pinned to whatever `0.17.0` version `bevy_asset_loader` itself pulls in transitively, since `bevy_asset_loader`'s own dynamic-asset manifests use this crate internally too — see the version-pin comment in `Cargo.toml` if bumping either one. Added to both `client` and `server` `Cargo.toml`s, since both may eventually need to load `.ron`/`.toml` data assets, not just `client`.

`chill_bevy_console` (crates.io) provides the in-game dev console (backtick to toggle) — see the console-gating convention below; it shapes how observers are registered throughout `client`.

Reflected types (e.g. anything Skein reads out of a `.glb`'s extras) are identified by Bevy's crate-qualified `TypePath`. Renaming a crate or moving a module changes that path — after the workspace split (crate renamed `prototype_19` → `client`), a previously-exported `.glb` had to be re-exported from Skein because its baked-in type references no longer matched. Expect this any time a crate/module housing reflected types gets renamed or moved.

## Architecture

`client/src/main.rs` is pure composition — a `Plugin` (`Prototype19`) listing feature plugins, plus the crate-root `add_observers_run_if!` macro (see conventions below). Game flow is a top-level state machine, but `GameState` itself — along with `VRState`, `ServerState`, `ModalMenuState`, and `InputDeviceState` — now lives in `shared::game_state`, not a client-only module, since `ServerState` needs to be visible to `server` too; `GameStatePlugin` (also in `shared::game_state`) registers all of them. `GameState`'s real flow is `AssetLoading -> MainMenu -> Lobby -> Loading -> InGame` (`AssetLoading` is the `#[default]` starting state now, not `MainMenu` — nothing that reacts to `OnEnter(GameState::MainMenu)` can run until `CommonAssets` finishes loading; see the `assets` module bullet below): the main menu's Connect button opens the QUIC connection directly, `on_connected` (`lifecycle::networking.rs`) lands the client in `GameState::Lobby` once it succeeds, and Lobby's own Play button is what actually requests a level load. Most gameplay/UI entities are scoped to a state via `DespawnOnEnter`/`DespawnOnExit` so they self-clean on transitions instead of needing manual teardown systems. Three further independent state machines layer on top of `GameState`: `VRState` (`Desktop`/`VR`, set once at startup from `main.rs`'s VR bootstrap), `ModalMenuState` (`Closed`/`Open` — the in-game pause menu, `ui/modal_menu.rs`, overlaying `GameState::InGame` without replacing it), and `InputDeviceState` (`KeyboardMouse`/`Gamepad`, continuously updated from raw input events — see `shared::game_state::track_last_input_device` — so UI like `hud.rs`'s control-tip icons can show the right device's glyphs).

Key modules (all under `client/src/`, now grouped into subdirectories — `controls/`, `dev/`, `gameplay/`, `lifecycle/`, `presentation/`, `ui/`, `assets/` — each with its own `mod.rs` rather than a flat file per module; bullets below name the module, not its full path):

- **`main.rs`** — beyond plain plugin composition, two decisions get made here that can't wait for a normal `Startup` system:
  - **VR/Desktop plugin choice**: `networking::is_vr_enabled_presync()` reads `config.toml`'s `vr` field via plain `std::fs` (not the `AssetServer`, which doesn't exist yet) *before* anything else in `Prototype19::build` runs, since which plugin group even gets added — `DefaultPlugins` vs. `add_xr_plugins(DefaultPlugins.build().disable::<PipelinedRenderingPlugin>())` — is a one-time choice that has to happen up front. `GameStatePlugin { vr_enabled }` (see above) and the VR-only plugins (`bevy_mod_xr::hand_debug_gizmos::HandGizmosPlugin`, `vr_controllers::VrControllersPlugin`, `OxrSessionConfig`) are gated on the same `vr_enabled` bool rather than added unconditionally and toggled via `run_if` — `VrControllersPlugin` in particular is actively broken without a real XR session (its `Startup`/`On<PlayerSpawned>` systems use `Single<Entity, With<XrTrackingRoot>>`, an entity that only exists once the XR plugins actually ran). Switching between desktop and VR needs a restart, same as most other desktop/VR-crossplatform games.
  - **Disabling client-side physics simulation**: the server is authoritative for physics, so the client only needs colliders and spatial queries (`SpatialQuery` raycasts/shapecasts — `targeting.rs`'s hover raycast, `character_controller.rs`'s grounding shape-casts), not to actually simulate anything. `PhysicsPlugins::default().build()` has `IntegratorPlugin`/`SolverPlugin`/`CcdPlugin`/`XpbdSolverPlugin` disabled — **not** `Time::<Physics>::pause()`, which would also stop broad/narrow-phase from running and leave spatial queries stale against moving colliders, since the entire inner `PhysicsSchedule` (including broad-phase) is skipped whenever `Time<Physics>` reports paused. This was confirmed by testing to be more than an architecture nicety: it also **fixed a real physics glitch on reconnect** that the client's own local solver fighting freshly-replicated `Transform` corrections used to cause. One visible tradeoff: `RigidBody::Dynamic` cubes/NPCs no longer predict their own motion locally between replication ticks — they only move when a new server `Transform` arrives — unlike `PlayerCharacter` movement, which stays smooth since it's driven directly by `character_controller.rs`'s kinematic move-and-slide, not the solver. Two follow-up fixes this needed, both found by testing rather than documented anywhere upstream:
    - `PhysicsSchedule`'s `ambiguity_detection` gets relaxed from `LogLevel::Error` (Avian's own default, appropriate when its full solver stack establishes a total system order) to `LogLevel::Warn` — with several solver plugins gone, ~21 system pairs lose that ordering and would otherwise panic at schedule-build time. Confirmed every ambiguous pair is between joint-related systems (this project spawns zero joints), compound/child-collider systems (colliders here live directly on the root rigid-body entity), or `trigger_collision_events` (nothing reads Avian's native `CollisionStarted`/`CollisionEnded` — `character_controller.rs` tracks its own `CharacterCollisions` from shape-casts instead) — none of which this project's own systems race on.
    - `Gravity` gets manually `init_resource`'d, since `IntegratorPlugin` (disabled) is normally what provides it, and `IslandSleepingPlugin`'s `resource_changed::<Gravity>` run condition panics at startup ("resource does not exist") without it — `Gravity` is inert data, not tied to a system of its own, so this is a safe minimal stand-in.
    - **Explicitly not disabled**: `SolverBodyPlugin`/`IslandPlugin`/`IslandSleepingPlugin`, despite the "solver" naming — confirmed by testing, not theory: disabling `SolverBodyPlugin` crashed the collider tree (`update_moved_collider_aabbs`) with an index-out-of-bounds panic, because it's shared per-body bookkeeping the broad-phase itself indexes into for every awake dynamic/kinematic body, not solving. Don't extend the disabled list to these without re-testing from scratch.
- **`player_character.rs`** — the client no longer spawns its own player character; the server does (see `server::networking::spawn_player_for_client`) and it arrives here via replication. Two separate reactions to that, for two different audiences:
  - `on_player_spawned` (`On<PlayerSpawned>`, a *targeted* server event — see `shared::server_events::PlayerSpawned`) fires only on the one client whose own character this is. It sets the `LocalPlayer` resource (`Some(spawned.entity)`) and *decorates* that already-existing entity with everything only the local player needs: `controls::player_controls()`, the FPS camera rig, `camera::player_camera(...)`. It does not spawn the character itself — that entity already exists by the time this observer runs.
  - `decorate_other_players` (a polling `Update` system, not event-driven — deliberately, since it needs to catch both already-replicated `PlayerCharacter` entities and ones that arrive later, and there's no single lifecycle moment that covers both) finds every `PlayerCharacter` that *isn't* `LocalPlayer` and gives it a visible `rig.glb` model (tagged `PlayerModel`) plus the `OtherPlayer` marker, so it doesn't get re-processed.
  - `LocalPlayer(pub Option<Entity>)` — the resource other modules (`targeting.rs`, `hud.rs`) read to know "which replicated entity is mine," rather than querying `With<PlayerCharacter>` and hoping there's only one (there won't be, once more than one player is connected). Initialized to `None` by `targeting.rs`'s `TargetingPlugin` (this module doesn't own its own init — worth knowing if this ever moves).
  - `PlayerModel` is defined here; `PlayerCharacter`/`PlayerCharacterSpawner`/`Selectable` and the `player(name, position)` bundle constructor live in `shared::player` now — see the "Shared simulation" section — since the server needs them too. There's no client-side player-name concept any more (a `PlayerName` resource, set from a main-menu text field, used to live here — the text field was removed in favor of `config.toml`-driven connection settings, see `networking.rs`'s bullet, and the dead resource was deleted along with it); every spawned player is just named `"Player"` server-side (see `spawn_player_for_client`).
- **`actions.rs`** — every `bevy_enhanced_input` `#[derive(InputAction)]` marker struct for the player, all in one file rather than defined near each handler (see the input convention below for why).
- **`controls.rs`** — owns the player's entire input surface: the `PlayerControls` input-context marker, every action *binding* (the definitions live in `actions.rs`) in one `Actions::<PlayerControls>::spawn` block (`controls::player_controls()`, a bundle-constructor spawned as a child of the player entity — mirrors `ui.rs`'s `panel()`/`button()` pattern of a plain function returning `impl Bundle`/`impl Scene`), cursor lock/unlock on state transitions, and the observers that translate raw input events into events other modules (now including the server) understand. Two different shapes, deliberately:
  - `on_movement`/`on_movement_stop`/`on_jump` → `commands.client_trigger(shared::client_events::Movement { direction })`/`Jump` — **not** a local `shared::character_controller::MovementInput`/`JumpInput` trigger anymore. The client has no local character-controller physics loop of its own to feed (see `player_character.rs`'s note on `CharacterControllerPlugin` running client-side too, in the "Shared simulation" section, for the nuance there); these events cross the network and the *server* is what turns them into `MovementInput`/`JumpInput` (`server::networking::on_movement`/`on_jump`), resolving the target entity from the sending connection itself, never from anything in the payload.
  - `attack`/`kill` → `shared::client_events`' `AttackAttempt`/`KillAttempt`, sent via `commands.client_trigger`. Each carries one `Entity` field — but it's the *target*, not the attacker/killer: `server::combat`'s `resolve_attack`/`resolve_kill` resolve who's acting from `attempt.client_id`, the same `ClientId`-resolution convention `Movement`/`Jump` use (see below), just with a target to name in addition. A client can't claim to be attacking on someone else's behalf here, only pick who it's attacking.
  - `shoot`/`spawn_npc` → client-local `SpawnCube`/`SpawnNpc` triggers, which `cube_spawner.rs`/`npc_spawner.rs`'s own observers immediately turn into `commands.client_trigger(SpawnCubeRequest { .. })`/`SpawnNpcRequest` — these *do* cross the network already, just via that one extra client-local hop rather than `controls.rs` sending the network event directly (unlike `Movement`/`Jump`/`AttackAttempt`/`KillAttempt`, which skip the local-event hop entirely). `main_menu` → closes the connection and returns to `GameState::MainMenu` (see `networking.rs`'s bullet below for the full reasoning).
  
  Also registers `TargetingPlugin`, since `Select`/`Deselect` are bound here alongside everything else the player can press. **The context marker and its `Actions<C>` must be components on the *same* entity** — `bevy_enhanced_input::add_input_context::<C>()` requires `C` and `Actions<C>` together (it registers `ContextActivity<C>` as a required component of `C`, and the evaluation system queries `(&ContextActivity<C>, &Actions<C>)` on one entity) — splitting them across parent/child silently disables the whole context with no compile error.
- **`events.rs`** — client-local events with no server-authoritative meaning: animation triggers (`AnimationFinished`, `PlayAnimationLooping`/`PlayAnimationOnce`), `LoadLevel`, `RespawnPlayer`, and the `SpawnCube`/`SpawnNpc` client-input triggers `controls.rs` fires before translating them into `shared::client_events`' `SpawnCubeRequest`/`SpawnNpcRequest`. The dividing line from `shared::client_events`/`shared::server_events` is exactly "would this cross the network" — see the combat request→resolve→confirm pipeline (`AttackAttempt`/`KillAttempt` → `Attack`/`Kill`, resolved in `server::combat` — see `client/src/combat.rs`'s bullet), or `controls.rs`'s `Movement`/`Jump`, for that shape. **`RespawnPlayer` is currently vestigial** — `console.rs`'s `respawn` command and `loading.rs` still fire it, but nothing observes it anymore (player spawning moved server-side; see `player_character.rs`). The `respawn` console command is a silent no-op today.
- **`lifecycle/networking.rs`** — opens the client's QUIC (`bevy_quinnet`) connection to the server (port hardcoded, `SERVER_PORT = 6000`, but the *address* is config-driven; skips cert verification since the server's cert is self-signed) and drives the post-connect state transition. `ServerAddress(pub String)` is the resource `on_connect_request` reads, defaulting to `"127.0.0.1"` and overwritten by `client/assets/config.toml`'s `server_ip` at `Startup` (`config::load_client_config`, now in its own `client/src/config.rs` file rather than here — see the `Commands`/config.toml paragraph above). Connecting is triggered by the main menu's Connect button (`ui/ui.rs`'s `connect_button`, `commands.trigger(Connect)`) — `on_connect_request` (`On<Connect>`) opens the connection (no-op if already open/opening, so a repeat press is safe), and `on_connected` (`OnEnter(ClientState::Connected)`) transitions straight to `GameState::Lobby`, not `InGame` — picking and loading an actual level is a separate step Lobby's own Play button drives (see `lifecycle/lobby.rs`). `on_disconnected` (`OnEnter(ClientState::Disconnected)`) is guarded against firing during `GameState::AssetLoading` — `ClientState::Disconnected` is `#[default]` and fires once on the very first frame, before `CommonAssets` has loaded, which used to force-transition to `MainMenu` early and panic every `OnEnter(GameState::MainMenu)` system needing `Res<CommonAssets>`. See `server/src/networking.rs` for the listening side and `shared::replication` for the full list of what's replicated. (The `PendingLevelId`/deferred-connect-until-Play design this bullet used to describe is gone — connecting and loading a level are two separate, sequential steps now, `MainMenu` → `Lobby` → `Loading`, not one combined action.)
- **`camera.rs`** — the player's camera bundle and skybox loading. `player_camera(asset_server, cubemap)` returns the `Camera3d`/TAA/SSAO/`Skybox`/`DistanceFog` bundle, but also takes `&mut Cubemap` and seeds its `image_handle` — the `Cubemap` resource (owned privately by this module, via `PlayerCameraPlugin`) is what the `Update`-scheduled `cubemap_loaded` system polls to reinterpret the flat `Ryfjallet_cubemap.png` as a proper cubemap array texture once loaded; if nothing seeds `image_handle`, `cubemap_loaded` early-returns forever and the skybox silently never appears. This coupling is why the resource is threaded through the constructor explicitly rather than left implicit. `DistanceFog`'s `color` (`FOG_COLOR`) deliberately matches `main.rs`'s `ClearColor` — with the `Skybox` insert currently commented out, the clear color *is* the background behind un-fogged geometry, so fog needs the same tint to blend into it rather than fading to a visibly different flat color. `FOG_START`/`FOG_END` (40.0/180.0) are chosen relative to existing gameplay distances, not arbitrarily — both `targeting::SELECT_RANGE` and `nameplate.rs`'s `FADE_END_DISTANCE` (30.0) sit well inside `FOG_START`, so fog never visibly interferes with targeting or nameplate readability.
- **`targeting.rs`** — the hover/select hub: `Hovered`/`Selected` resources, `raycast_from_center`, `select`/`deselect` observers, and the `bevy_mod_outline` integration. Also owns the `LocalPlayer` resource's *initialization* (`insert_resource(LocalPlayer(None))` in `TargetingPlugin::build`) even though the type itself is defined in `player_character.rs` — worth knowing if `LocalPlayer` or targeting ever moves, since that init is easy to lose track of. `raycast_from_center` excludes `LocalPlayer` from the raycast (via `SpatialQueryFilter::from_excluded_entities`) so you can't hover/select your own character. `deselect_when_out_of_range` clears `Selected` once the distance between `LocalPlayer` and the selected entity's `GlobalTransform` exceeds `SELECT_RANGE` — both systems no-op gracefully while `LocalPlayer` is still `None` (before `PlayerSpawned` arrives). `add_outline_component` is an `On<Add, WorldAssetRoot>` observer, not a `Selectable`-driven one — `AsyncWorldInheritOutline` only starts inheriting once the *same* entity's own `WorldAssetRoot` resolves (it checks `WorldInstance` on itself, not an ancestor), so outline components go on whichever descendant actually carries `WorldAssetRoot` (found by walking ancestors from wherever `WorldAssetRoot` was just added), not necessarily the `Selectable` entity itself.
- **`combat.rs`** — presentation only (sound, particles, clearing `Selected`, hiding corpses), reacting to events/state the server drives rather than deciding anything itself. The actual range check, damage application, and death detection are **fully server-side** now, in `server::combat::ServerCombatPlugin` (see the "Server" section) — there is no `shared::combat` plugin, `shared::combat.rs` only holds the data types (`HitPoints`, `Gcd`, `Dead`) both sides need to agree on.
  - `on_attack`/`on_kill` play a sound on the confirmed `Attack`/`Kill` server events (unchanged shape: `resolve_attack`/`resolve_kill` on the server take the *request* events `AttackAttempt`/`KillAttempt`, gate on `Gcd`/`ATTACK_RANGE`, then fire the *confirmed* `Attack`/`Kill` these react to).
  - `on_entity_died` reacts to `shared::server_events::EntityDied` — sound, particle effect at `died.position`, clears `Selected` if it pointed at whatever died. This is a real server→client event now (registered via `add_mapped_server_event` in `shared::replication`), fired by `server::combat::kill_zero_hp` *before* it mutates the entity — deliberately **not** inferred from `HitPoints`/the entity being removed, the way an earlier version of this did (`On<Remove, HitPoints>`): that fires for *any* removal, including a character despawning for a completely unrelated reason (returning to the main menu despawns every `InGame`-scoped entity at once via `DespawnOnExit`, which used to play a death sound/particle for every character in the level on every trip back to the menu). `EntityDied.position` is captured server-side and sent directly in the event payload rather than looked up from the entity client-side, since by the time this arrives the entity's own despawn-via-replication may already have landed.
  - `hide_dead` sets `Visibility::Hidden` on every entity `With<Dead>` (see `shared::combat::Dead` — a replicated component the server inserts instead of despawning immediately once `HitPoints` hits zero, so a corpse lingers for `DEAD_DURATION` before `server::combat::despawn_dead` actually removes it). **Deliberately a polling `Update` system, not an `On<Add, Dead>` observer** — confirmed by testing, not theory: a client that reconnects (main menu → `Play` again) gets already-`Dead` entities via `bevy_replicon`'s initial full-state sync, and that doesn't reliably fire `OnAdd` observers the way a live single-component insert during an ongoing session does, so an observer-based version left reconnected clients seeing dead things as still visible. This is the flip side of the "prefer observers" convention below — don't "fix" this back to an observer without re-testing the reconnect path specifically.
- **`animation.rs`** — a small but real animation state machine, composed from several independently-built pieces:
  - `Animations` resource: one shared `AnimationGraph` + a name→node `HashMap`, built once from `rig.glb`'s `named_animations`.
  - `PlayAnimationLooping`/`PlayAnimationOnce` — `EntityEvent`s that look up a clip by name and `AnimationTransitions::play(...)`, with/without `.repeat()`.
  - `AnimationFinished` — fired when a one-off animation's `ActiveAnimation::is_finished() && just_completed()`, with `entity` set to `root_ancestor::<ChildOf>(player_entity)` (e.g. `PlayerCharacter`, not the `PlayerModel` child the `AnimationPlayer` actually lives on).
  - `Idle` is the state-machine control token: present, `locomotion()` drives walk/idle/jump every frame straight off `LinearVelocity`/`Grounded`; absent, `locomotion()` skips that entity, leaving a one-off animation (attack, hurt) in exclusive control. `on_attack` removes `Idle` from the target and fires `"attack"`/`"hurt"` one-offs on attacker/target; `on_animation_finished` re-inserts `Idle` once the one-off completes, handing control back.
- **`fps_controller.rs`** — first-person camera look, gated by `chill_bevy_console::console_closed`. Also drives the visible `PlayerModel`'s yaw (not pitch, to avoid tilting the body) to track the camera — currently a permanent no-op since nothing spawns an entity with `PlayerModel` (the player has no visible mesh in first person). Kept intentionally rather than deleted: it's meant to become the anchor that rotates the model shown to *other* players once multiplayer exists.
- **`cube_spawner.rs`** — spawns `Cube` props. Random angular velocity via `noiz` (`NoiseRng`/`SNorm`, seeded from `elapsed_secs().to_bits()` — *not* a scaled-and-cast `as u32`, which saturates permanently at `u32::MAX` after ~71 minutes of runtime and was the cause of a real "all cubes spin identically" bug). **Deliberately** does not skip spawning when the spawn point overlaps existing geometry (the `shape_intersections` check's `continue` is commented out) — stacking cubes by spawning them into each other and letting Avian's solver push them apart is an intentional mechanic. Don't "fix" this to match `npc_spawner.rs`. `on_cube_spawned` parents the spawned entity under the current level's `LevelRoot` (see `loading.rs`) via `ChildOf` rather than giving it its own `DespawnOnExit` — cleanup on level reload comes for free from that, not from a tag on this entity.
- **`npc_spawner.rs`** — spawns `Npc` (`Character` + `Idle`, `RigidBody::Dynamic` capsule with `LockedAxes` locking all rotation, `rig.glb` model as a child). Same `noiz` random-rotation pattern as cubes. Unlike cubes, **does** skip spawning via `shape_intersections` — NPCs stuck in geometry is a bug, not a mechanic. Same `LevelRoot`-parenting as `cube_spawner.rs`, for the same reason. `decorate_npcs` also attaches a small `Mesh3d`/`MeshMaterial3d` quad above each NPC's head (from `npc_ui_quad::NpcUiQuad`, see below) via a fixed local `Transform` and plain `ChildOf` — no billboard system, so it turns with the NPC exactly like `rig.glb` does, rather than always facing the camera.
- **`npc_ui_quad.rs`** — demonstrates rendering `bevy_ui` onto a texture and displaying that texture on a rigid (non-billboarded) 3D quad, the same technique as Bevy's own `examples/ui/render_ui_to_texture.rs`: a second `Camera2d` targeting an off-screen `Image` via a `RenderTarget` component (its own component in this Bevy version, not a field on `Camera`) instead of the window, with a UI root pointed at it through `UiTargetCamera`. `setup_npc_ui_quad` (`Startup`) builds this once and stores the resulting `Rectangle` mesh + `StandardMaterial` handles in the `NpcUiQuad` resource `npc_spawner.rs`'s `decorate_npcs` reuses for every NPC — one shared render target for all of them, not one per instance, since the UI content here is static (just an "NPC" label). A per-NPC version showing each one's own name/HP would need its own `Image`/`Camera2d`/UI root per entity instead of sharing this resource.
- **`nameplate.rs`** — floating name + health-bar UI above `Character`/`HitPoints` entities, spawned reactively (`On<Add, HitPoints>`). Positioned every frame via `Camera::world_to_viewport`, not a 3D billboard quad — ordinary 2D UI repositioned to match a projected world point, which is what most games actually do for this. Fades out with distance (`FADE_START_DISTANCE`/`FADE_END_DISTANCE`), fading `TextColor`/`BackgroundColor` alpha directly since Bevy UI has no subtree-wide opacity. `track_nameplates` (the `Update` system doing all this every frame) is **not** a child of its target — deliberately: parenting a 2D UI `Node` under a 3D world entity would try to fold it into Bevy UI's own flexbox layout tree via the same `ChildOf` relationship the 3D transform hierarchy uses, which isn't how UI layout works and isn't why the target has a `Transform` in the first place. That means it gets none of `InheritedVisibility`'s automatic `ChildOf`-based propagation for free, so `track_nameplates` mirrors it manually: reads the target's own `Option<&InheritedVisibility>` and force-hides the nameplate if the target resolves to not-visible (e.g. `Dead`, see `combat.rs`'s `hide_dead`) — **`Option`, not a bare reference**, since most character root entities have no `Visibility`/`InheritedVisibility` component at all (only entities that render something, or have it explicitly inserted, get it — the target here is a physics/logic entity, the actual mesh is a separate child), and a bare `&InheritedVisibility` in the query would fail to match those entirely, which read as "target despawned" to the rest of this function and despawned every nameplate on the very next frame. `NameplatesVisible(pub bool)` (default `true`) is toggled by the console's `nameplates` command (`console.rs`) — `track_nameplates` force-hides every nameplate when it's `false`, checked alongside the existing target-visibility hiding. **Known perf hotspot, not yet fixed**: with many nameplates on screen, disabling them via this toggle measurably raised FPS (~30 FPS in informal testing) — the likely cause is `track_nameplates`'s `children.iter_descendants(nameplate_entity)` call, done for *every* nameplate *every frame* to find its `HealthFill`/text/background children (each call heap-allocates a traversal queue), plus unconditionally rewriting `Node.width`/`TextColor`/`BackgroundColor` even when the value hasn't changed (each write marks the UI node dirty for layout/paint). Not yet confirmed via profiling which of these actually dominates — the likely fix is caching each nameplate's child entities at spawn time instead of re-walking the hierarchy every frame, plus skipping writes when the value is unchanged, but do that after profiling with Tracy (see the "Commands" section) rather than guessing.
- **`console.rs`** — wraps `chill_bevy_console::ChillConsole` plus `avian3d::PhysicsDebugPlugin` and Bevy's `FpsOverlayPlugin`, both added permanently but disabled by default and toggled via console commands (`fps`, `physics_debug`) that flip runtime config resources (`FpsOverlayConfig.enabled`/`.frame_time_graph_config.enabled` — two independent flags — and `GizmoConfigStore::config_mut::<PhysicsGizmos>().0.enabled`) rather than adding/removing plugins. Also: `respawn`, `despawn_cubes`, `despawn_npcs`, `play_animation <clip>` (validates the name and lists available clips on a miss, rather than reporting false success), `controls` (the control scheme, now console-only — see `ui.rs`), and two more visibility toggles following the same flip-a-resource pattern: `nameplates` (`nameplate::NameplatesVisible`) and `hud` (`hud::HudVisible`).
- **`ui.rs`** — decluttered to a single always-visible `DataFrame` panel (HP/damage/range constants, hovered/selected info) plus the main menu; the old separate controls-hint/console/stats/selected-frame panels are gone, replaced by the `controls` console command. The main menu's `Quit` button is wired to a real `quit_button` observer (`commands.write_message(AppExit::Success)`) — `Options`/`Credits` still go to the shared `stub_button` (`info!("not implemented yet")`), since only `Quit` and `Play` do anything real so far.
- **`hud.rs`** — the always-visible in-game HUD: `data_frame` (the `DataFrame` debug panel), `hotbar` (ability slots with a shared radial GCD cooldown-sweep overlay, `assets/shaders/gcd_overlay.wgsl`, driven by a `UiMaterial`), `crosshair`, and `controls_tips` (a top-left panel listing every keyboard/mouse binding `controls.rs`'s `player_controls()` sets up — kept in sync with that list by hand, same as `console.ftl`'s `console-controls` text hint is; there's no single source of truth `bevy_enhanced_input` bindings could be introspected from automatically). `controls_tips` builds each row from the actual `KeyCode`s/`MouseButton`s a binding uses via `input_icons.rs` (see below) rather than hand-copied asset-path strings, and renders each key/button as its own `ImageNode` (`control_tip_icon`) rather than packing several glyphs into one `Text` run — see `input_icons.rs`'s doc comment for why PNGs won over the icon-font approach it replaced. `HudVisible(pub bool)` (default `true`, toggled by the console's `hud` command) and a `HudElement` marker tag every one of `in_game_scene`'s four independent root entities (they aren't siblings under one common `Node` — see `in_game_scene`'s `bsn_list!`) so `update_hud_visibility` can set `Visibility` on all of them without needing a shared parent; that system runs unconditionally every frame (not gated on `HudVisible` changing) since a `HudElement` can respawn after a level reload while the toggle is still off, and would otherwise default back to visible.
- **`input_icons.rs`** — maps `KeyCode`/`MouseButton` to the matching icon PNG in Kenney's CC0 "Input Prompts" keyboard/mouse pack, for `hud.rs`'s `controls_tips` panel. PNGs live in `assets/textures/input_prompts/keyboard_mouse/` (copied from `assets_src/input_prompts/Keyboard & Mouse/Default/` under the pack's own filenames — not re-keyed to the `KeyCode` variant name, so e.g. `KeyCode::Quote` maps to `keyboard_apostrophe.png`). The pack also ships these as a single icon font (`assets/fonts/input_prompts/`, still present but currently unused by anything) — this module used to wrap that font instead, but the PNGs have a real advantage the font glyphs didn't: `mouse_left.png`/`mouse_right.png`/`mouse.png` are genuinely distinct images, whereas the font's equivalent glyphs are pixel-identical (a font-level limitation found while separately fixing a real winding-direction bug in that font — several of its glyphs had a contour wound the same direction as the keycap background, rendering as solid blank squares under the nonzero fill rule; fixed via `fontTools` contour-reversal, unrelated to the PNG-vs-font choice itself).
- **`widgets.rs`** — shared, screen-agnostic UI building blocks (`panel`, `button`, tooltips) used by both the main menu and `hud.rs`. `Activate` is the one event a `Button` fires when "pressed," regardless of *how* — a real pointer press (`activate_on_press`, `On<Pointer<Press>>`) or gamepad/keyboard confirm while the button holds `InputFocus` (`ui.rs`'s `on_ui_confirm`) both funnel into it, so call sites only ever need to observe `Activate` once. **`activate_on_press` must be registered exactly once** — as the per-entity `on(activate_on_press)` inside `button()`'s own `bsn!` block, nowhere else. It was briefly *also* registered globally (`app.add_observer(activate_on_press)` in `WidgetsPlugin::build`, introduced alongside gamepad support and only caught because mouse-click testing lagged behind gamepad testing), which meant every real click fired `Activate` twice for every button in the game — cascading into `ui.rs`'s Play button sending two `LoadLevelRequest`s per click (see `server::level_state::LevelState`'s doc comment for the fallout that caused server-side, and why the fix there had to be independent of fixing this).
- **`lifecycle/loading.rs`** — **currently mid-rework, not a reliable description of working behavior** — `spawn_level` and `on_level_assets_loaded` are both literal `todo!()` stubs right now, and the module imports `assets::collections::LevelAssets`, a type that doesn't currently exist in `collections.rs` (a real compile error as of this writing — the asset-manifest rewrite described in the `assets` bullet below is landing in pieces). What's still real: level loading is a client-requests/server-decides/client-follows round trip, driven by an `On<LoadLevel>` observer (a client-local event, not to be confused with `shared::server_events::LoadLevel`) that validates the requested manifest path exists via a blocked-on `AssetReader::read` before registering it into `DynamicAssetCollections<GameState>` for `GameState::Loading` and transitioning there; the server (`server::networking::on_load_level_request`) is still what actually spawns the replicated `LevelRoot` entity, the client never creates its own. Don't trust the rest of the previously-documented `load_level`/`spawn_level`/`on_level_ready` chain (dynamic-asset-key resolution, `WorldInstanceReady` gating `InGame`) until this module stops containing `todo!()`s — read the file directly instead.
- **`assets/`** (`collections.rs`, `level.rs`, `manifest.rs`) — also actively in flux; treat the below as a snapshot, not a settled design:
  - `collections.rs`'s `CommonAssets` (`AssetCollection` derive, loaded via `LoadingState::new(GameState::AssetLoading).continue_to_state(GameState::MainMenu)` in `main.rs`) is the stable, working part — every asset the client needs regardless of level (models, sounds, skybox, UI fonts, input-prompt icon atlases), resolved from `assets/collections/common_assets.assets.ron` the same way `bevy_asset_loader`'s dynamic-asset-file mechanism always has.
  - `collections.rs` also declares `PreloadCollection` (`armature_rigs`/`world_rigs`/`skyboxes`/`audio`, each a `collection(typed, mapped)` `HashMap<AssetFileStem, Handle<T>>`) and a `PreloadBeacon` component (`collections: Vec<String>`, `load_radius`/`unload_radius`) — early scaffolding toward a proximity-based streaming/hot-set system (see the "Platform targets" section below for why), not yet wired to any spawning/unloading logic.
  - `level.rs`'s `Level` asset (`name`, `entry` — an `.ftl` key and a `.glb` path) is loaded directly via `bevy_common_assets`' `RonAssetPlugin::<Level>` (registered in `main.rs` against the `"level.ron"` extension, e.g. `assets/levels/start.level.ron`), independent of `bevy_asset_loader`'s dynamic-collection manifests. It deliberately has no `preload_collections`/`collection` field any more — the intent (per the file's own `TODO` comment) is to derive a level's preload set purely from whichever `PreloadBeacon`s are in range of the `entry` `.glb`'s player-spawner entity, not a hand-authored list that could drift from beacon reality; not implemented yet.
  - `manifest.rs`'s `Manifest` asset (`metadata`, `entry_points: HashMap<String, String>`) and the top-level `assets/manifest.toml` are an early stub for resolving level ids to `.level.ron` paths — `assets/mod.rs`'s `LevelsManifest` struct alongside it is unused dead code so far.
- **`particles.rs`** — `bevy_hanabi` particle effect setup.

## Shared simulation (`shared/src/`)

`shared` is compiled into both `client` and `server`. It's the actual home of the "always multiplayer" split now: simulation logic that must produce identical results on both sides, plus the network-message types that cross between them.

- **`replication.rs`** — `SharedReplicationPlugin` is the single place both binaries register what crosses the network: `.replicate::<T>()` for every replicated component (`LevelRoot`, `Transform`, `PlayerCharacter`, `Character`, `CharacterController`, `Name`, `HitPoints`, `Gcd`, `GroundDetection`, `Collider`, `DesiredMotion`, `RigidBody`, `LinearVelocity`, `Selectable`, `Dead` — note several of these, e.g. `Collider`/`RigidBody`/`GroundDetection`, are effectively static per-character config rather than real per-tick state; replicating them is harmless but not necessary, the client could construct them locally instead), plus `add_mapped_client_event`/`add_mapped_server_event` for every client↔server event type. `Dead` being replicated (not just the transient `EntityDied` event) is deliberate — see `client/src/combat.rs`'s `hide_dead` bullet for why presentation needs the persistent state, not only the one-shot event. Both this component list and the event list must stay identical between `client` and `server` builds — `bevy_replicon`'s `ProtocolHash` check disconnects a client whose registration doesn't match the server's.
- **`player.rs`** — `PlayerCharacter`/`PlayerCharacterSpawner`/`Selectable` marker components, and `player(name, position) -> impl Bundle`: the server-authoritative capsule (`RigidBody::Kinematic`, `Collider::capsule(0.4, 1.0)`, `CharacterController`, starting `HitPoints { 100, 100 }`, etc.) both `server::networking::spawn_player_for_client` and (indirectly, via replication) `client::player_character` build on. `client`'s own `PlayerModel`/`OtherPlayer` markers and camera/input decoration are *not* here — this module only owns what the server needs to spawn a valid character, not how it's presented.
- **`character_controller.rs`** — the kinematic character controller. Server-only: `CharacterControllerPlugin` is registered in `server/src/main.rs` only — the client has no local character-controller physics loop of its own (`controls.rs`'s `on_movement`/`on_jump` send `Movement`/`Jump` network events rather than triggering `MovementInput`/`JumpInput` locally), so there's no client-side smoothing between replication ticks today. **Currently gutted**: every system/observer body in this file is a `todo!()` stub as of an in-progress rewrite toward genuine lightyear-idiomatic client-side prediction (`lightyear_inputs_*`/`PredictionPlugin`, neither wired up yet — see `client/src/main.rs`'s note on why `PredictionPlugin` is currently disabled) — the previous move-and-slide/ground-detection/gravity/damping mechanics (originally lifted from an avian3d example) have been intentionally removed; see git history for the prior implementation. Every component type (`CharacterController`, `Character`, `GroundDetection`, `Grounded`, `DesiredMotion`, etc.) and the `MovementInput`/`JumpInput` event shapes are unchanged and still replicated/triggered exactly as before — only the systems that acted on them are stubbed.
- **`combat.rs`** — data types only, no plugin and no systems here despite the name: `HitPoints`, `Gcd` (the shared global-cooldown timer every ability gates on), `Dead` (a timer-backed component the server inserts instead of despawning immediately once `HitPoints` hits zero — see `server::combat` and `client/src/combat.rs`'s bullets for the full kill→`Dead`→despawn pipeline), and the `DAMAGE`/`ATTACK_RANGE`/`GCD_DURATION`/`DEAD_DURATION` constants. The actual combat *resolution* — range checks, damage application, death detection, firing `server_events::Attack`/`Kill`/`EntityDied` — is fully server-side now, in `server::combat::ServerCombatPlugin` (see the "Server" section). There is no `SharedCombatPlugin`.
- **`client_events.rs`** / **`server_events.rs`** — the network message types themselves, split by direction (client→server / server→client), all `#[derive(EntityEvent or Event, Serialize, Deserialize, ...)]`. Any type with an `Entity` field needs `#[entities]` on that field plus `MapEntities`, and must be registered via `add_mapped_client_event`/`add_mapped_server_event` (not the plain variant) in `replication.rs` — see the entity-mapping convention below. Note the two different shapes in use: `Movement`/`Jump` carry no `Entity` at all, since there's nothing to name beyond "the sender" (identity always resolves from the connection); `AttackAttempt`/`KillAttempt` carry one `Entity` field too, but it's the *target* being acted on, not the actor — the actor still resolves from the connection the same way, in `server::combat`'s `resolve_attack`/`resolve_kill`.
- **`level.rs`** — `LevelRoot { id: AssetPath<'static> }`, `#[require(Transform, Visibility)]`. That require exists specifically because of replication: the client's mirror of this entity only ever gets whatever's explicitly `.replicate::<T>()`-registered, and `Visibility`/`InheritedVisibility`/`ViewVisibility` are never replicated (meant to be computed locally from `Visibility`, the same way `GlobalTransform` is computed locally from `Transform`) — without the require, the client's copy had none of them at all, which produced a real `bevy_app::hierarchy` B0004 warning (parent missing `InheritedVisibility` while its `WorldAssetRoot` child had it) and inconsistent visibility propagation for the whole level subtree.
- **`cube_spawner.rs`**/**`npc_spawner.rs`** — same spawn logic as before the split (see the equivalent `client/src/` bullets above for the noiz-seeding and overlap-check details, which didn't change), now living here so `server` can run the same authoritative spawn decisions.

## Server (`server/src/`)

Headless — `MinimalPlugins`, not `DefaultPlugins` — which means anything `DefaultPlugins` normally gives you for free has to be added or registered explicitly. This has bitten repeatedly enough to be worth internalizing as a pattern, not just a list of one-off fixes: `StatesPlugin` (for `bevy_replicon`'s states) and `bevy::log::LogPlugin` (or nothing prints, at all, ever) are added directly; `.init_asset::<Mesh>()`/`.init_asset::<Image>()` are called manually (normally `ImagePlugin`'s/rendering plugins' job); and the `bevy` dependency in `server/Cargo.toml` explicitly enables `reflect_auto_register` (client gets this for free through `default-features = true` → `default_app` → `3d`/`2d`, none of which the headless server has).

- **`main.rs`** — pure composition, mirroring `client/src/main.rs`'s convention. Notably: `AssetPlugin { file_path: "../client/assets", .. }` — `server` has no `assets/` directory of its own; level geometry lives in `client/assets/` (see the note on why, above), so the server points its default filesystem asset source there instead of duplicating it. Also adds `bevy::gltf::GltfPlugin`, `bevy::world_serialization::WorldSerializationPlugin`, and `bevy_skein::SkeinPlugin` — this trio is what makes headless `.glb` loading (with full Skein-reflected components, including `ColliderConstructor`) possible at all. None of them depend on `bevy_render`/`bevy_pbr`/`bevy_scene` (checked directly in their `Cargo.toml`s) — the whole GLTF/Skein/world-asset pipeline was built render-independent, which is exactly why this works without a window or GPU.
- **`networking.rs`** — the QUIC endpoint (`start_endpoint`, binds `0.0.0.0:6000` with a self-signed cert) and everything server-authoritative:
  - `on_movement`/`on_jump` (`On<FromClient<Movement>>`/`On<FromClient<Jump>>`) resolve the target entity from `request.client_id` (`ClientId::Client(entity)`) — **never** from the payload, since the client's own connection entity *is* its player character (see `player.rs` above). `server::combat`'s `resolve_attack`/`resolve_kill` follow the same pattern for *who's acting* (see `combat.rs`'s bullet below) — those two do still take an `Entity` from the payload, but only to say who the action targets, not who's performing it.
  - `on_load_level_request`/`on_level_ready` — spawns the replicated `LevelRoot`, loads the server's own local `WorldAssetRoot` (for real, headless Avian colliders — see the `main.rs` bullet), transitions `LevelState` to `LevelLoaded(id)`, and broadcasts `shared::server_events::LoadLevel`. `on_load_level_request` rejects any request while `LevelState` isn't `Idle` (see `level_state.rs`'s bullet below for why and for the known gap this doesn't close). Also this is where connected players get their character: `spawn_player_for_client` inserts the `player(...)` bundle onto a client's own connection entity (+ `Replicated`) and fires a *targeted* `PlayerSpawned` (`SendTargets::Single(ClientId::Client(client_entity))`) so that one client — and only that one — learns which entity is its own. Two call sites: the batch loop in `on_level_ready` (for clients already connected when the level finishes loading) and `on_authorized_client_connected` (gated on `LevelState::LevelLoaded(_)`, for clients joining after). **Non-obvious consequence of the dedup gate**: only the *first* `LoadLevelRequest` a server ever accepts in its lifetime actually does anything. Every later client — including one that disconnected and reconnected via the main menu's `Play` flow (see `client/src/networking.rs`'s bullet) — gets the already-existing `LevelRoot` for free via ordinary replication the moment it's authorized (triggering its own `spawn_level`/`on_level_ready` unconditionally, same as any replicated `LevelRoot`) and its player character from `on_authorized_client_connected`'s own independent `LevelState::LevelLoaded(_)` check; that client's *own* `LoadLevelRequest`, sent by its `load_level` the same as always, arrives and gets silently rejected by the dedup gate — which is fine, it was never needed. Don't be surprised the request "does nothing" for a reconnecting client; that's by design, not a bug.
  - `on_connection_lost` reads `bevy_quinnet::server::ConnectionLostEvent` directly (via `Res<NetworkIdMap>` to resolve the entity) and despawns the client's entity immediately, rather than waiting on `bevy_replicon_quinnet`'s own despawn (built on the same event, in its `process_server_events`) to eventually remove `ConnectedClient`/`AuthorizedClient` and trigger the `on_client_disconnected`/`on_authorized_client_disconnected` observers below (which are now purely informational — despawning still fires their `Remove` triggers, since despawn removes every component). Pre-empting it like this is safe: `bevy_replicon_quinnet` explicitly tolerates the entity having already been despawned by the time it runs. This doesn't make disconnection *faster* to detect, though — that's bounded by QUIC's `max_idle_timeout` (`quinn`'s default: 30s, per RFC 9308 §3.2; `bevy_quinnet` doesn't expose a way to configure it), not by anything in this observer chain.
  - **Known gap**: nothing despawns a disconnecting client's other `Replicated` entities (beyond the connection entity itself, which *is* their player character here, so that part's covered) — relevant once a client owns more than just its own character.
- **`combat.rs`** — `ServerCombatPlugin`, the authoritative half of combat (`shared::combat` only holds the data types now — see the "Shared simulation" section). `resolve_attack`/`resolve_kill` (observers on `FromClient<AttackAttempt>`/`FromClient<KillAttempt>`) gate on `Gcd`/`ATTACK_RANGE`, apply damage or an instant kill, and fire the confirmed `Attack`/`Kill` server events. `kill_zero_hp` (`Update`, filtered `Without<Dead>` so it's idempotent) checks every `HitPoints <= 0` entity, broadcasts `EntityDied { entity, position }` (*before* mutating anything — client presentation needs a still-valid `Transform`-derived position, and needs this as an unambiguous "died in combat" signal distinct from the entity simply being removed for some unrelated reason later), then inserts `Dead::default()` and removes `Selectable`/`RigidBody` — **not** an immediate despawn any more. `tick_dead`/`despawn_dead` age `Dead`'s timer and despawn the entity for real once it finishes (`DEAD_DURATION`, in `shared::combat`) — the corpse lingers, replicated, for that long first. Nothing yet gates `on_movement`/`on_jump`/`resolve_attack`/`resolve_kill` on `Without<Dead>` — see the "What's still genuinely missing" note at the top of this file.
- **`level_state.rs`** — `LevelState`, named that specifically instead of `ServerState` to avoid colliding with `bevy_replicon`'s own `ServerState` (`Running`/`Stopped`, tracking the QUIC listener) — both are in scope together wherever `bevy_replicon::prelude::*` is imported. Three variants: `Idle` / `Loading(AssetPath<'static>)` / `LevelLoaded(AssetPath<'static>)` — the latter two carry the level's id, which `on_load_level_request` uses to reject any further `LoadLevelRequest` while a level is already loading or loaded, regardless of id (switching to a genuinely different level isn't supported yet either way — see the top-of-file gap note). Still gates whether a newly-connecting client gets a character immediately (`on_authorized_client_connected`) or has to wait for the level to actually finish loading first, same as before. **Deliberately a plain `Resource`, not a Bevy `States` type** — `bevy_replicon` can (and does) trigger `on_load_level_request` twice in the same frame when two `LoadLevelRequest`s arrive in the same network batch (this is exactly what the `widgets.rs` double-`Activate` bug produced client-side before *that* was fixed), and `States`/`NextState` only applies a transition once per frame via the dedicated `StateTransition` schedule — a `next_state.set(...)` in the first observer call wouldn't be visible to `Res<State<_>>` in the second call until next frame, so a `States`-based dedup check silently does nothing against the exact same-frame-double-trigger case it exists for. A plain resource mutated directly makes the check-and-set atomic within one observer call.

## Notable conventions

- Interaction/selection targeting uses a raycast against `Selectable`-tagged entities each frame (`targeting::raycast_from_center`), writing into `Hovered`/`Selected` — the hub to touch when changing targeting behavior.
- Input is entirely `bevy_enhanced_input`: actions are marker structs (`#[derive(InputAction)]`), all defined together in `client/src/actions.rs` — deliberately *not* near each handler — bound together in `controls.rs`'s single `Actions::<PlayerControls>::spawn` block, handled via observers (`On<Fire<T>>`, `On<Start<T>>`, `On<Complete<T>>`). Centralizing the action definitions paid off exactly as intended: `Movement`/`Jump`/`AttackAttempt`/`KillAttempt` have since become `commands.client_trigger(...)` calls without touching `actions.rs` at all. `shoot`/`spawn_npc` route through one extra client-local event (`SpawnCube`/`SpawnNpc`, translated to `SpawnCubeRequest`/`SpawnNpcRequest` by `cube_spawner.rs`/`npc_spawner.rs`) rather than `controls.rs` sending the network event directly, but they do already cross the network — see `controls.rs`'s bullet above.
- **Component lifecycle observers are used liberally as a state-machine mechanism**, not just for setup/teardown: `On<Add, T>`/`On<Remove, T>` drive real gameplay reactions (e.g. `Idle`, `Grounded` transitions feeding the animation system), not just cleanup. Prefer this over a polling `Update` system with a manual guard/marker component when what you're reacting to might legitimately land on a *different* entity or at an unpredictable *later* time than whatever you'd otherwise assume "setup time" to be — that's exactly the shape of bug a polling+guard system produces silently (see the outline system's history: it originally reacted to `Selectable` and walked descendants eagerly, which broke for `Npc` because its `WorldAssetRoot` child didn't exist yet at that point in the same spawn call).
- **`EntityEvent` vs plain `Event`**: reach for `#[derive(EntityEvent)]` (a field literally named `entity`, or `#[event_target]` on another field) when you want `commands.entity(e).observe(...)` scoping or propagation. It only supports *one* formal target per event — for a two-entity relationship (e.g. `shared::server_events::Attack`'s attacker/target), put the side you want scoped-observe on as `entity`, and the other as a plain field.
- Cross-cutting gameplay events are Bevy observers/triggers (`commands.trigger(...)`), not plain systems reading queues.
- **Server never trusts a client-supplied entity for "who sent this"** — resolve identity from `On<FromClient<T>>`'s `request.client_id` (`ClientId::Client(entity)`, the client's own connection entity — see `shared::player`/`server::networking`) instead. `Movement`/`Jump`/`AttackAttempt`/`KillAttempt` all follow this — the latter two do still carry a client-supplied `Entity`, but only to say who the action *targets*, never who's performing it. The same logic applies in reverse for entity-mapped events: any client/server event carrying an `Entity` needs `#[entities]` on that field plus `#[derive(MapEntities)]`, and must be registered via `add_mapped_client_event`/`add_mapped_server_event` rather than the plain variant — the mapping only resolves correctly for entities that are themselves replicated, so referencing a non-replicated entity in one of these maps to nothing meaningful on the other side.
- **Console-gating**: gameplay observers that shouldn't fire while the dev console is open are registered through the crate-root `add_observers_run_if!` macro (`main.rs`, `pub(crate) use`d) with `chill_bevy_console::console_closed` as the condition. Lifecycle/cleanup observers (`on_player_spawned` in `player_character.rs`, `on_movement_stop` in `controls.rs`) are registered as plain, ungated `app.add_observer(...)` instead — gating a player-spawn reaction like this was a real bug once (back when the client did its own local spawning: opening the console in the main menu before pressing Play silently dropped the one-shot spawn trigger forever, since observer triggers aren't queued/retried, leaving no player and no camera). Lifecycle/spawn handlers must stay ungated; only "please do X now" player-input actions should be gated.
- Hierarchy walks reuse `Query<&Children>::iter_descendants`/`iter_descendants_depth_first` and `Query<&ChildOf>::iter_ancestors`/`root_ancestor` (inherent `Query` methods, no extra trait import) rather than hand-rolled recursion — see `targeting.rs`, `animation.rs`, `nameplate.rs` for the pattern.
