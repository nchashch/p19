# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Bevy 0.19 (Rust, edition 2024) 3D game prototype. **Cargo workspace** with three members: `client` (the actual game — everything playable today), `server` (a minimal headless stub, not yet real), and `shared` (an intentionally near-empty library, scaffolding for whatever eventually needs to live on both sides). No tests currently exist in the repo.

The workspace exists in anticipation of an "always multiplayer" architecture — even singleplayer would run a local client *and* server, simulation on the server / presentation on the client, so hosting real multiplayer later is "open a port" rather than a rewrite. That split hasn't happened yet: all gameplay logic (physics, combat, spawning, rendering, UI, animation) currently lives in `client`, written as ordinary local-authority Bevy code. `bevy_replicon_quinnet`/`bevy_quinnet` (networking) and `bevy_asset_loader` (structured content loading) are real dependencies already present but **unused** — nothing in `client` references them yet. Don't assume replication or structured asset loading exists just because the crates are there.

## Commands

```sh
cargo build -p client         # debug build of the game
cargo build -p server         # debug build of the server stub
cargo build --workspace       # build everything
cargo run -p client           # run the game
cargo run -p server           # run the (currently inert, headless) server stub
cargo check --workspace       # fastest way to verify compile errors across all members
cargo clippy --workspace
```

There is no test suite. Run commands from the workspace root (`prototype_19/`) — Bevy's default asset resolution is relative to each crate's own `CARGO_MANIFEST_DIR` at compile time, not the process's CWD, which is why `assets/`/`assets_src/` live inside `client/` (`client/assets/`) rather than at the workspace root; moving them back out will break asset loading.

`../build.sh` (one level up, outside this workspace) cross-builds a release binary inside a `steamrt-sniper` podman container for Steam Runtime compatibility. It runs `cd prototype_19 && cargo build --release`, which now builds the whole workspace — any packaging step downstream that expects a binary literally named `prototype_19` needs updating to `client`/`server`.

## Dependency layout

Root `Cargo.toml` is the workspace manifest: `[workspace.package]` for shared `edition`/`version`, `[workspace.dependencies]` centralizing every dependency's version (or local path) in one place. Member `Cargo.toml`s reference them via `dep.workspace = true` rather than redeclaring versions. Two things worth knowing if you touch this:
- A member **cannot** override `default-features` on a `dep.workspace = true` reference, even if the workspace entry explicitly sets `default-features = true`. `server`/`shared` need a smaller `bevy` feature set than `client` (headless, no rendering), so they declare `bevy` directly with their own `default-features = false` instead of inheriting it — see `server/Cargo.toml`/`shared/Cargo.toml`.
- Path dependencies in `[workspace.dependencies]` resolve relative to the **workspace root** (where the root `Cargo.toml` lives), not relative to whichever member references them. The workspace root is at the same location the old single-crate root used to be, so these paths are unchanged from before the workspace split (`../bevy_mod_outline`, etc. — not `../../`).

Several dependencies are **not** pulled from crates.io — they're path-dependencies on sibling checkouts one directory up from the workspace root (`../<crate>`), i.e. forked/vendored versions of these libraries:

- `polyanya` (`../polyanya`) — navmesh pathfinding
- `rerecast` (`../rerecast/crates/rerecast`) — navmesh generation
- `bevy_mod_outline` (`../bevy_mod_outline`) — selection/hover outlines
- `bevy_vello` (`../bevy_vello`) — vector graphics rendering
- `bevy_seedling` (`../bevy_seedling`) — audio
- `audionimbus` (`../audionimbus/audionimbus`) — spatial audio

If something doesn't behave like upstream docs suggest, or a symbol can't be found, check the sibling checkout's source directly rather than assuming crates.io behavior — these may be patched/ahead-of/behind the published versions. `bevy_mod_outline` in particular carries a local fix: `pipeline_key.rs`'s `DerivedPipelineKey::new` used to force `motion_vector_prepass` to `false` for the `Stencil`/`FloodInit` pass types regardless of the view's actual state, which crashed (wgpu bind-group-layout validation error) when outlining a skinned mesh with `TemporalAntiAliasing` enabled. Fixed by letting them inherit the view's real flag like the `Volume` pass type already did. Worth upstreaming; if this crate is ever re-vendored, check whether the fix needs reapplying.

`bevy`, `avian3d` (physics), `bevy_skein`, `bevy_enhanced_input`, `bevy_asset_loader`, and `bevy_hanabi` (particles) are pulled from crates.io, but `[workspace.dependencies]` keeps commented-out `path = "../..."` lines for all of these too — if a registry release is broken or lags a needed feature, swapping to the sibling checkout is the established escape hatch.

`chill_bevy_console` (crates.io) provides the in-game dev console (backtick to toggle) — see the console-gating convention below; it shapes how observers are registered throughout `client`.

Reflected types (e.g. anything Skein reads out of a `.glb`'s extras) are identified by Bevy's crate-qualified `TypePath`. Renaming a crate or moving a module changes that path — after the workspace split (crate renamed `prototype_19` → `client`), a previously-exported `.glb` had to be re-exported from Skein because its baked-in type references no longer matched. Expect this any time a crate/module housing reflected types gets renamed or moved.

## Architecture

`client/src/main.rs` is pure composition — a `Plugin` (`Prototype19`) listing feature plugins, plus the crate-root `add_observers_run_if!` macro (see conventions below). Game flow is a top-level state machine (`game_state::GameState`: `MainMenu -> Loading -> InGame`), and most gameplay/UI entities are scoped to a state via `DespawnOnEnter`/`DespawnOnExit` so they self-clean on transitions instead of needing manual teardown systems.

Key modules (all under `client/src/`):

- **`character_controller.rs`** — generic kinematic character controller built on Avian3D's `MoveAndSlide` primitive. Owns only the `FixedUpdate` physics-integration loop: grounding via shape-casting, gravity, movement damping, slope climb/slip logic. It does **not** own input response — turning input into `DesiredMotion`/jump impulses is `controls.rs`'s job.
- **`player_character.rs`** — the player entity itself: `respawn_player` despawns any existing one and spawns the character-controller entity plus its children (`controls::player_controls()`, the FPS camera rig, `camera::player_camera(...)`). Defines the entity-identity markers other modules query against — `PlayerCharacter`, `PlayerCharacterSpawner`, `PlayerModel` (see `fps_controller.rs`) — plus `Character`/`Idle` (the animation state machine's backbone, see `animation.rs`, declared here rather than there) and the `PlayerName` resource (set from the main menu's text field, defaults to `"Player"`). Deliberately thin — input binding, camera/skybox setup, and cursor-lock state all live in their own modules now and just get threaded through as bundles/resources.
- **`controls.rs`** — owns the player's entire input surface: the `PlayerControls` input-context marker, every `bevy_enhanced_input` action definition and binding in one `Actions::<PlayerControls>::spawn` block (`controls::player_controls()`, a bundle-constructor spawned as a child of the player entity — mirrors `ui.rs`'s `panel()`/`button()` pattern of a plain function returning `impl Bundle`/`impl Scene`), cursor lock/unlock on state transitions, and the observers that translate raw input events into domain events other modules understand (`on_jump`/`on_movement` → `shared::character_controller`'s `JumpInput`/`MovementInput`, `shoot`/`spawn_npc` → `cube_spawner`/`npc_spawner` triggers, `main_menu` → `GameState`). Also registers `TargetingPlugin`, since `Select`/`Deselect` are bound here alongside everything else the player can press. **The context marker and its `Actions<C>` must be components on the *same* entity** — `bevy_enhanced_input::add_input_context::<C>()` requires `C` and `Actions<C>` together (it registers `ContextActivity<C>` as a required component of `C`, and the evaluation system queries `(&ContextActivity<C>, &Actions<C>)` on one entity) — splitting them across parent/child silently disables the whole context with no compile error.
- **`camera.rs`** — the player's camera bundle and skybox loading. `player_camera(asset_server, cubemap)` returns the `Camera3d`/TAA/SSAO/`Skybox` bundle, but also takes `&mut Cubemap` and seeds its `image_handle` — the `Cubemap` resource (owned privately by this module, via `PlayerCameraPlugin`) is what the `Update`-scheduled `cubemap_loaded` system polls to reinterpret the flat `Ryfjallet_cubemap.png` as a proper cubemap array texture once loaded; if nothing seeds `image_handle`, `cubemap_loaded` early-returns forever and the skybox silently never appears. This coupling is why the resource is threaded through the constructor explicitly rather than left implicit.
- **`targeting.rs`** — the hover/select hub: `Hovered`/`Selected` resources, `raycast_from_center`, `select`/`deselect` observers, and the `bevy_mod_outline` integration. `add_outline_component` is an `On<Add, WorldAssetRoot>` observer, not a `Selectable`-driven one — `AsyncWorldInheritOutline` only starts inheriting once the *same* entity's own `WorldAssetRoot` resolves (it checks `WorldInstance` on itself, not an ancestor), so outline components go on whichever descendant actually carries `WorldAssetRoot` (found by walking ancestors from wherever `WorldAssetRoot` was just added), not necessarily the `Selectable` entity itself.
- **`combat.rs`** — `Attack` is an `EntityEvent` with *two* entities (`entity` = target, the formal `EntityEvent` target; `attacker` = plain field, not itself dispatch-scoped). `attack`/`despawn_cube` funnel through a shared `kill_entity` helper (sound + particle effect + despawn + clear `Selected`).
- **`animation.rs`** — a small but real animation state machine, composed from several independently-built pieces:
  - `Animations` resource: one shared `AnimationGraph` + a name→node `HashMap`, built once from `rig.glb`'s `named_animations`.
  - `PlayAnimationLooping`/`PlayAnimationOnce` — `EntityEvent`s that look up a clip by name and `AnimationTransitions::play(...)`, with/without `.repeat()`.
  - `AnimationFinished` — fired when a one-off animation's `ActiveAnimation::is_finished() && just_completed()`, with `entity` set to `root_ancestor::<ChildOf>(player_entity)` (e.g. `PlayerCharacter`, not the `PlayerModel` child the `AnimationPlayer` actually lives on).
  - `Idle` is the state-machine control token: present, `locomotion()` drives walk/idle/jump every frame straight off `LinearVelocity`/`Grounded`; absent, `locomotion()` skips that entity, leaving a one-off animation (attack, hurt) in exclusive control. `on_attack` removes `Idle` from the target and fires `"attack"`/`"hurt"` one-offs on attacker/target; `on_animation_finished` re-inserts `Idle` once the one-off completes, handing control back.
- **`fps_controller.rs`** — first-person camera look, gated by `chill_bevy_console::console_closed`. Also drives the visible `PlayerModel`'s yaw (not pitch, to avoid tilting the body) to track the camera — currently a permanent no-op since nothing spawns an entity with `PlayerModel` (the player has no visible mesh in first person). Kept intentionally rather than deleted: it's meant to become the anchor that rotates the model shown to *other* players once multiplayer exists.
- **`cube_spawner.rs`** — spawns `Cube` props. Random angular velocity via `noiz` (`NoiseRng`/`SNorm`, seeded from `elapsed_secs().to_bits()` — *not* a scaled-and-cast `as u32`, which saturates permanently at `u32::MAX` after ~71 minutes of runtime and was the cause of a real "all cubes spin identically" bug). **Deliberately** does not skip spawning when the spawn point overlaps existing geometry (the `shape_intersections` check's `continue` is commented out) — stacking cubes by spawning them into each other and letting Avian's solver push them apart is an intentional mechanic. Don't "fix" this to match `npc_spawner.rs`.
- **`npc_spawner.rs`** — spawns `Npc` (`Character` + `Idle`, `RigidBody::Dynamic` capsule with `LockedAxes` locking all rotation, `rig.glb` model as a child). Same `noiz` random-rotation pattern as cubes. Unlike cubes, **does** skip spawning via `shape_intersections` — NPCs stuck in geometry is a bug, not a mechanic.
- **`nameplate.rs`** — floating name + health-bar UI above `Character`/`HitPoints` entities, reactive (`On<Add, HitPoints>`, no polling). Positioned every frame via `Camera::world_to_viewport`, not a 3D billboard quad — ordinary 2D UI repositioned to match a projected world point, which is what most games actually do for this. Fades out with distance (`FADE_START_DISTANCE`/`FADE_END_DISTANCE`), fading `TextColor`/`BackgroundColor` alpha directly since Bevy UI has no subtree-wide opacity.
- **`console.rs`** — wraps `chill_bevy_console::ChillConsole` plus `avian3d::PhysicsDebugPlugin` and Bevy's `FpsOverlayPlugin`, both added permanently but disabled by default and toggled via console commands (`fps`, `physics_debug`) that flip runtime config resources (`FpsOverlayConfig.enabled`/`.frame_time_graph_config.enabled` — two independent flags — and `GizmoConfigStore::config_mut::<PhysicsGizmos>().0.enabled`) rather than adding/removing plugins. Also: `respawn`, `despawn_cubes`, `despawn_npcs`, `play_animation <clip>` (validates the name and lists available clips on a miss, rather than reporting false success), `controls` (the control scheme, now console-only — see `ui.rs`).
- **`ui.rs`** — decluttered to a single always-visible `DataFrame` panel (HP/damage/range constants, hovered/selected info) plus the main menu; the old separate controls-hint/console/stats/selected-frame panels are gone, replaced by the `controls` console command.
- **`loading.rs`** — level (`Level.glb`) loading and the `Loading -> InGame` transition.
- **`particles.rs`** — `bevy_hanabi` particle effect setup.

## Notable conventions

- Interaction/selection targeting uses a raycast against `Selectable`-tagged entities each frame (`targeting::raycast_from_center`), writing into `Hovered`/`Selected` — the hub to touch when changing targeting behavior.
- Input is entirely `bevy_enhanced_input`: actions are marker structs (`#[derive(InputAction)]`), defined near whichever module owns their handler, bound together in `controls.rs`'s single `Actions::<PlayerControls>::spawn` block, handled via observers (`On<Fire<T>>`, `On<Start<T>>`, `On<Complete<T>>`).
- **Component lifecycle observers are used liberally as a state-machine mechanism**, not just for setup/teardown: `On<Add, T>`/`On<Remove, T>` drive real gameplay reactions (e.g. `Idle`, `Grounded` transitions feeding the animation system), not just cleanup. Prefer this over a polling `Update` system with a manual guard/marker component when what you're reacting to might legitimately land on a *different* entity or at an unpredictable *later* time than whatever you'd otherwise assume "setup time" to be — that's exactly the shape of bug a polling+guard system produces silently (see the outline system's history: it originally reacted to `Selectable` and walked descendants eagerly, which broke for `Npc` because its `WorldAssetRoot` child didn't exist yet at that point in the same spawn call).
- **`EntityEvent` vs plain `Event`**: reach for `#[derive(EntityEvent)]` (a field literally named `entity`, or `#[event_target]` on another field) when you want `commands.entity(e).observe(...)` scoping or propagation. It only supports *one* formal target per event — for a two-entity relationship (e.g. `combat::Attack`'s attacker/target), put the side you want scoped-observe on as `entity`, and the other as a plain field.
- Cross-cutting gameplay events are Bevy observers/triggers (`commands.trigger(...)`), not plain systems reading queues.
- **Console-gating**: gameplay observers that shouldn't fire while the dev console is open are registered through the crate-root `add_observers_run_if!` macro (`main.rs`, `pub(crate) use`d) with `chill_bevy_console::console_closed` as the condition. Lifecycle/cleanup observers (`respawn_player` in `player_character.rs`, `on_movement_stop` in `controls.rs`) are registered as plain, ungated `app.add_observer(...)` instead — gating `respawn_player` was a real bug once (opening the console in the main menu before pressing Play silently dropped the one-shot spawn trigger forever, since observer triggers aren't queued/retried, leaving no player and no camera). Lifecycle/spawn handlers must stay ungated; only "please do X now" player-input actions should be gated.
- Hierarchy walks reuse `Query<&Children>::iter_descendants`/`iter_descendants_depth_first` and `Query<&ChildOf>::iter_ancestors`/`root_ancestor` (inherent `Query` methods, no extra trait import) rather than hand-rolled recursion — see `targeting.rs`, `animation.rs`, `nameplate.rs` for the pattern.
